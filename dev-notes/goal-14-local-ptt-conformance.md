## 已比對一致的格式

- 看板列表日期、作者、`□` 標題標記分別從第 13、18、31 欄開始（欄位自 1 起算，以終端顯示寬度計）。
- 抽查的推文時間從第 68 欄開始，至第 78 欄結束。冒號差異不表示整行寬度改變。
- 推文方式選單 `您覺得這篇文章 1.值得推薦 2.給它噓聲 3.只加→註解 [1]?` 與 `確定[y/N]:` 提示一致。
- 標題、作者、推文數搜尋提示，以及回覆文章的 F／M／B／Q 選單文字一致。
- 從看板返回我的最愛後，頁首仍可能保留 `看板《…》`；兩邊都能觀察到，不能單靠這段文字認定目前仍在文章列表。
- 發文種類選單結構一致，分類文字依看板設定而異；Gossiping 與 Test 的分類不同不構成格式不相容。
- 重複登入提示相同。保留分支的新舊測試連線皆可操作；刪除分支使原測試連線關閉，新連線正常進入主選單。
- 多頁文章的 `第 n/m 頁`、百分比與 `第 xx~yy 行` 結構一致；42 行正文涵蓋三頁，PageDown、跳至末頁及回首頁均已走過。
- 搜尋結果使用 `系列《看板》`，結果編號重新計數；作者加標題條件、負值推文門檻與離開搜尋均已比對。不存在的標題搜尋保留原列表，未顯示一個空文章列表，與正式站 `093.txt` 的結果形態一致。
- 作者本人按 X 直接進入箭頭輸入；他人文章有推／噓／箭頭選單。發布後回到文章列表的行為與正式站 `035.txt` 一致。
- 刪文確認 `請確定刪除(Y/N)?[N]`、取消及刪除中提示一致；本機查詢已刪除 AID 顯示 `找不到這個文章代碼(AID)，可能是文章已消失，或是你找錯看板了`。

## `luit` 轉碼限制

本機 `luit -encoding big5` 將「應」顯示為 `⿅`。以 UAO 編碼固定文字再經 `luit` 輸出，也能重現「回應 → 回⿅」。這是比對工具的解碼差異，不能直接作為站台提示文字的 fixture。

目前客戶端經 `ptt-client` 使用 `uao-js` 解碼。收錄本機 fixture 應保留原始位元組或經相同解碼路徑產生文字，不將 `luit` 轉碼產生的字元替換加入解析規則。

## 客戶端整合測試發現

以下使用本機 Vite 代理及現有 browser/core 程式，透過獨立 Node 測試程式注入真實 `ptt-client`；不是網頁 UI 自動化驗證，也未修改 repo 的執行邏輯。

1. **接收訊息上限**：沿用 `blobSize: 1024` 時，收到 2,154 bytes 的 WebSocket 訊息直接拋出 `Receive message length(2154) greater than buffer size(1024)`。代理將 Telnet 解碼後的 TCP data 送為 WS 訊息，其邊界與長度不保證符合此常數。後續整合測試僅在獨立程式設定 65,536，這是隔離問題用的設定，不是修正。
2. **AID 操作**：原生終端可用 `#1ghzv4gk` 開啟本輪原文；同文章僅用 AID 呼叫客戶端讀取失敗，帶 AID 與編號時寫入又遭身分不符拒絕。僅使用已核對的列表編號可讀取並發出短推文。缺少網址列是已知格式差異，但尚未完成因果定位，不能宣稱所有錯誤皆由此造成。
3. **連續推噓**：一次推成功後立即噓，客戶端回報只能使用箭頭；稍後重新登入後，噓與箭頭皆成功。看板設定顯示開放噓文與快速連推；尚未確認是其他限制或客戶端狀態辨識問題。
4. **自動分段**：中英混合、空白行與符號草稿可規劃 6 段，但傳送回傳 `uncertain / 0 / 6`。讀回原文未看到該草稿，未盲目重試。另用不同草稿透過原生終端逐段傳送，6 段與核心聚合均成功，僅證明這組格式可還原，不能代替自動傳送成功。

以下保留當時的修正方向；2026-09-21 的完成狀態見下方：

- 接收上限：短期在本機代理適配訊息大小，必須驗證任意切點、Big5 與 ANSI 跨訊息；長期建議調整接收端的串流處理與有界緩衝，消除「每個 WS 訊息至多 1,024 bytes」的假設。
- 文章身分：短期在每次編號操作前重新核對身分；長期建議把 Q 資訊與原生 AID 導覽納入取得／驗證流程，網址列僅作額外資訊，同時涵蓋刪文造成編號移動。
- 分段傳送：先補回失敗階段與確認畫面的可追查證據，再依送達證據區分未送／已送／不確定；不以加長固定等待或自動重送取代定位。
