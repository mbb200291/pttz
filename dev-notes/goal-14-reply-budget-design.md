# 長回文傳送預算

## 已確認需求

網頁版每份草稿最多送出 30 則實體推文，取代 500 全形／1000 半形上限。此為介面產品政策，不屬於白皮書聚合規則。計數包含回覆樓號、尾標、空白行及橋接片段。

## 設計

- browser 在開啟輸入框時，以既有取消式容量探測取得當前文章的輸入容量與帳號；取消並確認返回後才交付規劃器，不發表探測內容。
- core 提供可選的公開準備 API，將 replyId 解析成樓號。規劃器同步計算草稿實際片段數，UI 不重做編碼或切段。
- 規劃器限定當次連線／文章準備結果，失效回報可重新準備的錯誤。UI 丟棄舊準備請求，切换目標重新取得，不跨看板套用容量。
- UI 顯示「剩餘 N / 30 則」、「超出 N 則」或「計算中…」。容量未確認、計畫無法還原或超限時不可開始送出；輸入和完整草稿仍保留。準備失敗提供重試。
- UI 將 maxFragments=30 傳入送出 API。browser 重新實測並完整規劃後，先檢查上限再送出第一則。既有分段續送仍保留原始計畫，不能藉修改上限改變已開始的操作。
- 其他客戶端可自訂上限或不設定；核心不內建 30。fake gateway 提供確定容量的同一規劃器。
- 計數與送出共用草稿正規化：CRLF 轉為 LF，去除整份草稿末端連續的空白與換行（包含半形空白、全形空白與 Tab）。只處理尾端，正文內部的空白與空白行保留；既有開頭正規化行為不在此次變更範圍。輸入框保留使用者輸入，不在打字時移動游標或刪除文字。純空白草稿計為 0 則且不能送出。

## 提交界線

1. 中斷符號改為 `\`：sender、receiver、測試、fixture 與對應規則文件同一個 commit，不包含 30 則政策。
2. 30 則預算與即時計數：容量準備 API、UI、末端空白正規化、測試及對應文件同一個 commit。

## 驗證與實作順序

1. 先完成中斷符號的獨立修正與提交，再補片段預算測試：30 可送、31 零寫入、超過 1000 半形但未超過片段上限可送；窄容量與樓號、尾標、內部空白行計入，尾端連續空白與換行不計入。
2. 公開準備 API、失效保護與共用規劃器；fake 與 terminal 路徑都支援。
3. Composer 即時計數、重試及送出防護；Article 綁定目前目標，防止非同步舊結果覆蓋。
4. 將白皮書移除產品字數／則數上限，同步規則 fixture 索引、UI README 與實作筆記。
5. 離線測試、建置及 lint。未經本次實站授權不連線發表測試內容。
