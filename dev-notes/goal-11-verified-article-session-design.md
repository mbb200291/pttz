# Goal 11：可驗證的文章工作階段

## 目標

讓 `@pttzzz/browser` 能在確定 PTT 終端仍停留於同一篇文章時直接執行回文、評分、編輯等文章操作；只有在位置不明或身分不符時才重新定位。同時保留既有 `@pttzzz/core` 契約及重新定位能力，避免因快取錯誤而把寫入送到其他文章。

## 邊界

- 此設計是 browser 核心實作層的終端工作階段管理，不改白皮書規則。
- 不改 `PttGateway`、`PttzzzClient` 或既有 UI 呼叫方式。
- UI 中的文章資料是顯示快取，不代表終端位置；是否可直接寫入只由 browser 層判斷。
- 不依賴計時器猜測位置，也不因「上一次開過此文」便直接寫入。

## 狀態模型

瀏覽器核心實作 `@pttzzz/browser` 私下保存一筆可重用的文章工作階段：

- `unknown`：目前沒有足以授權文章寫入的終端證據。
- `article`：最後一次完整驗證位於指定文章，保存文章識別與當時的終端快照。

文章識別保存 `board`、可用時的 `index` 或 `aid`、標準化後的作者與標題。連線事件、登入、原始按鍵及其他終端導覽會使工作階段失效並遞增版本；已開始的舊版本寫入在送出正文前會再次檢查版本。

看板、推文類別選單與推文輸入框不保存成可跨操作重用的狀態。它們只在單次操作內由目前畫面辨識，避免把過期的提示框狀態當成下一次寫入依據。

## 文章工作階段

成功讀取文章後可建立 article session，但只有終端畫面仍能驗證下列資料時才有效：

1. 畫面是文章閱讀器，而不是看板列表、提示框或連線錯誤。
2. 畫面標頭中的看板、作者與標題符合目標文章。
3. 目標含 AID 時，既有 AID 查核仍須通過；不能只相信文章索引。
4. session 版本尚未被其他終端導覽或斷線失效。

篩選或搜尋列表上的編號是相對位置，不是看板文章編號。這類文章必須先取得 AID 才能供後續寫入；若無法取得 AID，核心仍可顯示讀取結果，但拒絕以該相對編號重新定位或送出內容。

寫入前的 `acquireArticleContext` 先嘗試驗證現有 session。驗證成功便直接使用；失敗則沿用現有流程進入看板、定位文章、重新開啟及核對身分。重新定位仍失敗時停止，不送出正文。

## 推文狀態轉移

回文評分仍把 `推N樓`／`噓N樓` 放在 PTT 原生 `→` 類別中。

他人的文章：

```text
article --X--> push-menu --3--> neutral push-input --正文--> confirm --y--> article
```

作者本人的文章：

```text
article --X--> neutral push-input --正文--> confirm --y--> article
```

每個箭頭都必須先觀察到來源狀態，再送出按鍵，並等待目標狀態。畫面可能分批更新，因此判斷以狀態條件為準，不以固定延遲代表完成。按下 `y` 後也必須確認畫面回到相同看板、作者與標題的文章；若無法直接證明，進入後述讀回確認，且不得自動重送。

若要求 `neutral` 卻明確進入原生 `推` 或 `噓` 的空白輸入框，可用 Ctrl-C 取消、使 session 失效並回報未送出。若逾時或畫面仍可能停在類別選單，則不盲送 Ctrl-C，因 PTT 可能把非數字按鍵解讀為預設推文類別。不得把回文評分降級為文章推噓，也不得自動重試不確定的寫入。

## 送出結果的讀回確認

「已送出」與「終端已回到可重用的文章畫面」是兩項不同事實。終端未及時回到閱讀器時，不立即把操作暴露為失敗或要求使用者判斷，而由 browser 依序完成下列確認：

1. 等待 PTT 離開確認提示並回到相同看板、作者與標題的文章閱讀器。
2. 第一階段逾時後，優先取得並以已驗證的 AID 重新讀取同一篇文章。一般看板文章若當下無法取得 AID，可沿用絕對文章編號，但仍須核對看板、作者與標題；篩選列表的相對編號不得用於讀回定位。
3. 比較送出前後的原始 thread events，確認相同作者、PTT 原生類別與正文出現一筆新的事件。比對使用送出前的符合筆數或事件基線，不能僅因文章中已存在相同文字便判定成功。
4. 讀回使用 final article source，不以 partial snapshot 判定不存在。短暫的終端更新延遲可進行有限次、只讀的重新讀取；不得再次送出原命令。
5. 找到新增事件後回報 `sent`、更新 article session 與畫面。只有連線不可用、AID 無法取得、完整讀回失敗或事件仍無法區分時，才保留 `uncertain`。

這套確認適用於一般推文、巢狀回覆、回文推噓、撤回與回文編輯控制事件；即使控制事件不在最終 UI 顯示，仍以原始事件確認。原生文章推／噓則連同 `推`／`噓` 類別一起比對。

送出前保存的基線、預期事件及讀回差異只存在 browser 內部，不加入 `@pttzzz/core` 公開規則資料，也不把技術細節顯示給使用者。

## 產品呈現

- 操作進行時只在原控制項顯示「送出中」。
- 讀回確認成功後直接更新內容與數字，不顯示成功提示。
- 終端返回逾時但仍在自動讀回時，不顯示紅色警告或狀態機說明。
- 所有只讀確認都完成後仍無法判定，才在原控制項旁顯示「尚未同步」與「重新整理」；原操作保持防重複鎖定。
- `not-sent` 可以提供簡短、可操作的重試提示；`uncertain` 的底層原因只寫入開發診斷，不直接出現在 UI。

## 狀態失效

以下情況將 article session 設為 `unknown`：

- 斷線、重新登入或底層回報 closed/error。
- 執行首頁、看板、文章列表、搜尋、最愛或其他會移動畫面的指令。
- 畫面與保存的文章識別不符。
- 推文流程出現非預期畫面、逾時或送出結果不確定。
- 寫入期間版本改變，或無法證明寫入後已回到同一篇文章。

成功確認送出且畫面仍為同一篇文章時可以更新 session；舊相容介面若要求成功後回到看板，則使 article session 失效。

## 診斷

開發模式記錄推文流程輸入正文前的終端快照、經過時間，以及出站動作的語意名稱，例如 `open-push-menu`、`select-neutral`、`cancel`。密碼畫面會被省略，草稿正文不寫入診斷。

這能協助區分「程式真的多送按鍵」與「畫面更新漏讀」。終端快照仍可能含帳號、文章內容與 IP，只存在本機記憶體；分享前仍須自行遮蔽。工作階段的重用與失效理由目前只供 browser 內部判斷，不承諾為公開診斷介面。

## 相容策略

- 公開 core/browser 契約與回傳型別維持不變；狀態追蹤是 browser 私有實作。
- 現有呼叫方不需知道 session 是否被重用。
- 無法驗證時一律回到既有重新定位路徑，因此舊情境仍可運作。
- 第一階段讓推文型文章寫入使用 session，包括一般推文、巢狀回覆、回文推噓、撤回及回文編輯；文章本文編輯、刪文與回覆到看板仍走既有定位流程。一般搜尋與列表分頁不改語意。
- 不修改 `ptt-client` 套件；在 adapter 內封裝畫面辨識、狀態失效及序列化。

## 測試策略

1. 以真實終端文字建立可重播 transcript，驅動「收到某按鍵後逐步出現哪些畫面」，而非直接把畫面跳到預期結果。
2. 驗證同一文章 session 可直接操作，且不發出回看板與重開文章按鍵。
3. 驗證 session 過期、文章不同、AID 不符及斷線後都走重新定位。
4. 覆蓋非作者 `X → 選單 → 3 → →輸入框` 與作者 `X → →輸入框`。
5. 驗證所有出站動作順序；意外原生推／噓、重複操作、逾時及不確定結果均不送正文。
6. 以送出前後的原始事件 transcript 覆蓋相同舊文字、延遲出現、partial 不完整、AID 不符、連線中斷及控制事件讀回。
7. 保留既有 gateway contract tests，確認 `@pttzzz/core` 使用方式與結果語意沒有改變。

## 完成條件

- 已驗證仍在同一篇文章時，文章寫入不重新退出／進入。
- 位置不明時仍能安全重新定位，且不會對錯誤文章送出內容。
- 回文推噓只會透過 `→` 送出帶樓號前綴的控制文字。
- transcript 測試能偵測漏送、多送、錯序及畫面尚未就緒便送下一鍵。
- 終端返回未及時完成時，能優先以 canonical AID（或經完整身分核對的絕對文章編號）與原始事件增量確認絕大多數實際成功的操作，不把舊的同文事件誤認為本次送出。
- UI 不顯示內部狀態機或風險說明；正常成功無提示，只有最終未同步狀態提供簡短的重新整理操作。
- 原有 browser、core、Web 測試、建置、lint 與套件 smoke verification 通過。
