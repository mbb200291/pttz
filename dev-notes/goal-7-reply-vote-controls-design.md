# Goal 7 回文推噓控制修正設計

## 問題

目前 `Article` 將「作者只能用 `→` 回覆自己的文章」套用到所有 Composer 模式，導致作者回覆特定樓層時也無法選擇推／噓。這與 PTTzzz 的回文解析模型不符：針對樓層的推噓由內容 pattern 表達，可使用 PTT 的 `→` 類別送出。

回文卡片的推噓按鈕則在送出後立刻進入 pending 狀態，但要等 PTT 成功回應才更新票數與選取狀態。等待期間按鈕被鎖住且沒有視覺上的成功回饋或失敗訊息，因此看起來像無法點擊。

## 行為定義

### 直接回覆文章

- 文章作者只能選擇 `→`，並顯示 PTT 警語「作者本人, 使用 → 加註方式」。
- 非作者維持推／→／噓三種 PTT 原生類別。

### 回覆特定樓層

- 不受文章作者限制，所有登入使用者均可選擇推／→／噓。
- PTTzzz 統一以 PTT 的 `→` 類別送出，並以內容 pattern 表達語意：
  - 推：`推x樓 回覆內容`
  - →：`回x樓：回覆內容`
  - 噓：`噓x樓 回覆內容`
- 推／噓 pattern 同時形成可見的巢狀回覆，並計入目標樓層的回文評分。

### 回文卡片推噓

- 點擊後立即套用 optimistic UI，顯示新的選取方向與票數。
- 同一樓層在 PTT 回應完成前維持鎖定，避免重複送出。
- PTT 成功後重新載入文章確認狀態。
- PTT 失敗時回復點擊前的狀態、解除鎖定，並在討論串上方顯示失敗原因。
- 實際送出仍沿用現有 `votePush`／`withdrawPushVote`，其底層使用 `→` 與隱藏 pattern，不受作者不能推噓自己文章的限制。

## 實作範圍

- `Article.tsx`：依 Composer 模式決定 `neutralOnly`；格式化樓層回覆；調整回文投票的 optimistic state 與錯誤呈現。
- 現有 `Composer`、`PushThread` 與 adapter 介面保持不變，避免新增抽象。
- 不修改 `dev-notes/spec.md`。

## 驗證

- 作者直接回覆文章時，推／噓仍停用。
- 作者回覆特定樓層時，三種方向均可選。
- 特定樓層的三種回覆方向均以正確內容及 raw `neutral` 送出。
- 回文卡片投票在 promise 尚未完成時已顯示 optimistic 結果且阻擋連點。
- 回文卡片投票失敗時回復原狀並顯示原因。
- 完整測試、TypeScript build 與 lint 通過。
