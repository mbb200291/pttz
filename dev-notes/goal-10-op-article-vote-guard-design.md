# Goal 10 作者文章推噓防護設計

## 目標

PTT 不允許作者推或噓自己的文章；作者只能使用箭頭類別加註。PTTzzz 應在送出前反映這項限制，避免作者點擊看似可用的文章推噓按鈕後沒有任何結果。

## UI 行為

- 完整文章載入後，以不分英文字母大小寫的 PTT ID 比對目前使用者與文章作者。
- 若目前使用者是作者，文章層級的「推」與「噓」按鈕保持顯示但設為 disabled。
- disabled 按鈕旁固定顯示：`作者不能推噓自己的文章，可使用回覆加註。`
- 「回覆此文」按鈕保持可用，讓作者以 PTT 的箭頭類別新增加註。
- 非作者閱讀文章時，推噓 UI 與送出流程完全維持現況。
- 未登入時不顯示作者提示；既有文章推噓顯示方式不變。

固定顯示文字比 disabled button tooltip 更可靠：滑鼠、鍵盤與觸控使用者都能直接理解限制，也不需要新增 toast 或全域通知系統。

## 防護位置

`Article` 使用既有 `normalizePttId()` 建立 `isArticleAuthor`。這個值同時用於：

1. 傳入文章層級 `VotePair.disabled`。
2. 顯示作者限制提示。
3. 在 `handleArticleVote()` 開頭直接 return，防止程式呼叫或未來 UI 改動繞過 disabled button。

Adapter 現有防護不移除。若 UI 判斷因資料過期而未阻擋，PTT 回傳作者只能使用箭頭加註時，adapter 仍不得送出推或噓內容。

本次不修改回文卡片的推噓。作者仍可依現有規則對其他使用者的回文加分或扣分。

## 錯誤處理

作者點擊被停用的按鈕不會觸發 handler，也不會送出 `X`、推或噓至 PTT。限制原因由固定文字直接呈現，因此不產生暫時性錯誤狀態。

若非作者的正常推噓被 PTT 拒絕，仍沿用目前 adapter `{ ok: false }` 行為；這不屬於本 Goal。

## 測試策略

- 作者 ID 完全相同時，文章推與噓按鈕皆 disabled，並顯示固定提示。
- 作者與目前使用者只有大小寫不同時，仍視為作者。
- 作者觸發文章推噓 handler 時不呼叫 adapter action。
- 非作者的文章推噓按鈕保持可用，不顯示作者提示，正常呼叫既有 action。
- 回文層級推噓按鈕不因文章作者身分而停用。
- 執行相關 UI 測試、完整 `npm test`、lint 與 build。

測試使用 mock adapter，不會對真實 PTT 送出推噓。

## 不在本階段處理

- 自訂 tooltip、toast 或 modal。
- 修改 PTT 本身的作者限制。
- 改變作者回覆文章的 Composer 或預設箭頭類別。
- 其他 PTT 推噓失敗原因的 UI 錯誤訊息。
