# 補充

## ptt回文聚合處理

1. 符合以下規則，將同個作者的分散回文視為同一個回文
   - 連續回文或不連續回文但時間間隔不大於k分鐘，且最後一個字不是回文終止符（以下符號視為回文終止符）
     - `。`
     - `.`
     - `!`
     - `?`
     - `！`
     - `？`
     - `;`
     - `；`
   - 顯示上移除“回x樓“這段文字
   - 特殊符號位於回文末端，用於標示回文必須與後續回文合併：`||`
   - 若單行佔滿，則句子直接拼接下句，若無佔滿則下句保持獨立一行拼接，此處的佔滿需依照實際ptt的單行回覆長度上限而定義

2. 對某個回文的回文，用以下規則識別
   - “回x樓：...." <- 此處的回x樓作為識別該回文應該是對第x個回文的嵌套回文，依此類推。x 指向原始 PTT 推文樓號，一行一樓
   - 類似pattern
     - `回x樓`
     - `回xf` / `回xF`
     - `推x樓 xxxxxx`  # 此處的xxxx視為回文部分，且同時對x樓加分
     - `噓x樓 xxxxxx`  # 此處的xxxx視為回文部分，且同時對x樓加分
     - `TO xf`
     - `reply to xf`
     - `>>xf`
3. 對回覆的回覆，也需聚合，將以上符合的聚合規則整段作為對回覆的嵌套回覆。回覆到聚合卡片內任一原始樓號，都要指向同一張聚合卡；沒有前綴的續行只能繼承上一段的結構目標，不能跨不同目標聚合
4. 純投票、撤回等控制事件不能參與可見內容聚合
5. 嵌套回文限制最深x層，超過則僅視為放在第x層的回文，x先設定為3
6. ~對文章的讚數或扣分數用聚合後第一層回文的“推”總數~ <= 擱置此規則
7. ~對回文的讚或扣分數也類似，用聚合後的回文，且綁定在該回文者~
8. 作者的回文需有標籤標示為原發文者
9. 作者的文章編輯則視為對最接近的回文的回覆
10. 對文章的推噓按鈕，若從pttzzz發出，會以單一的“推”, “噓”發表至ptt
11. 解析規則，若遇到單純的”推“，”噓“則視為對文章的單純加扣分，不在pttzzz上顯示該回文

## 閱讀體驗 - Basic

- 開啟文章後看到部分內容需幾乎即時載入（不超過0.5秒），完整文章和下方回文區塊可稍後載入，但也需要能近乎即時逐步渲染，不應等到所有回文讀入後再一次渲染
- 進入看板看到文章列表的時間需近乎即時載入（不超過0.5秒）
- 看板文章可隨著滾動自動載入
- 自動預覽圖片和youtube影片
- 基本文章讀相關操作，包含搜尋文章、查詢文章id、搜尋文章id、篩選指定推噓文數文章
- 有按鈕能切換原始ptt推文顯示，和pttzzz進階顯示

## pttzzz編輯功能詳述

1. 發文功能，文章編輯頁，插入圖片按鈕
2. 回文
3. 對已有的回文的回覆功能，解析規則如同先前"ptt回文聚合處理"提及，但編輯功能統一用“回x樓：“這個格式
4. 對回文的讚和扣分按鈕，解析規則如下

```
推x樓       ==> 計入x樓一則加分，且不需額外顯示回文
x樓推一個    ==> 計入x樓一則加分，且不需額外顯示回文
噓x樓      ==> 計入x樓一則扣分，且不需額外顯示回文
```

若加扣分透過pttzzz介面，則統一送出“推x樓“、“噓x樓“
~注意此處我希望介面能強迫推和噓要走一般回文的推噓（加分必定只能推，扣分必定只能走噓），不能用回覆，這樣能套用ptt看板的推噓文限制~ <= 此段規則修正，pttzzz，對回覆的加扣分，都僅使用解析規則進行，使用ptt內建的推噓文類型，都採記在對文章的家扣分。從pttzzz介面送出的回文加扣分，都使用一般回覆
。另外解析規則，同一個id，同時存在推與噓時採最後方向；同方向重複仍只算一票。從我們ui方面，請阻擋同個id重複的推或噓可以被送出。
5. 使用以下格式作為收回對回文的推噓
   ```
   撤回我對x樓的推
   撤回我對x樓的噓
   ```
6. 對已有的回文的讚和扣分按鈕
7. 修改文章
8. 可修改或刪除某則回文，但可展開回文編輯歷史紀錄：解析規則類似如下，可先以行為單位替換

```

補充我在 12樓 說的：... => Append模式
修正我在 12樓 的說法：... => Replace模式
更正一下我在12樓的回覆：... => Replace模式
撤回我在11~13樓的發言 => Withdraw模式

```

前端會照這個規格解析，而我們這邊的修改按鈕，統一用“補充我在x樓發言：“、”更正我在x樓發言：“、"撤回我在x~y樓發言“
Withdraw模式刪除掉的回文，需保留一個空格
此處修改僅限於解析後的body內容，不能破壞原始的解析規則（避免解析規則被重新覆蓋）
> Append／Replace 指令只解析最外層指令。更新後的 body 為 opaque 
> payload，不再套用回覆、投票或撤回 pattern；編輯不得改變原始事件的
> replyTo、投票目標、投票方向或可見性。
