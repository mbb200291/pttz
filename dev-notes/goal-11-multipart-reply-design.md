# Goal 11：長回文自動分段傳送設計

狀態：設計提案，待審閱；尚未實作或修改白皮書。

## 1. 目標與範圍

使用者編輯一則完整回文，系統自行計算 PTT 可用容量、拆段、依序送出，最後在支援規則的客戶端還原為一則討論。使用者不需自行計算單行字數、插入續接符或重複輸入樓號。

- 支援回覆文章及回覆其他回文。
- 回覆其他回文的所有實體推文使用原生 `→`；不因分段額外投票。
- 支援中英混排、已驗證的 PTT 相容符號、主動換行與空白行。
- 不截斷文字、不以空白填滿容量、不把草稿中的換行直接當終端 Enter 傳送。
- 不以「本機看起來是一則」代替可由文章原始資料重新解析的持久語意。
- 本次不把回文編輯、撤回、純推噓控制命令自動拆段。這些命令不是一般文字，須另行設計；既有單則操作保持原契約。
- 發文、回覆文章到看板及文章編輯不屬於本功能。

## 2. 現況與已確認的問題

### 2.1 傳送端

- `apps/web/src/components/Composer.tsx` 使用固定 80 bytes 的粗估計數；超過就禁止送出。
- `packages/core/src/pushWire.ts` 同樣使用固定 80 bytes，將非 ASCII 一律估為 2 bytes。
- `packages/core/src/client.ts` 與 `packages/browser/src/gateway.ts` 對加入 `回N樓：` 或編輯前綴後的完整內容再檢查；因此 UI 剩餘量與實際送出量不一致。
- `submitPushFromCurrentArticle` 將整段內容加上 Enter 一次傳送。沒有拆段、逐段收據或續送進度模型。
- 現有 UI 對部分 `sent/uncertain` 結果採重新整理後關閉窗格。此流程不代表所有分段已送出，不可直接套用到多段操作。

### 2.2 接收端

白皮書 [MERGE-001／002／003](../docs/whitepaper/pttzzz-core.md#b-合併回文) 與 `packages/core/src/pushAggregator.ts` 的現況：

| 前一段 | 是否可續接 | 合併後兩段間的字元 |
| --- | --- | --- |
| 滿行，無終止符 | 符合其他條件時可以 | 無 |
| 未滿行，無終止符 | 符合其他條件時可以 | `\n` |
| 句號等終止符結尾，無 `||` | 不可以 | 分成不同討論 |
| 滿行，以 `||` 結尾 | 可越過終止符 | 無 |
| 未滿行，以 `||` 結尾 | 可越過終止符 | `\n` |

**`||` 是續接許可，不是直接串字或換行指令。** 它不放寬作者、對象、控制事件與非連續片段五分鐘等限制。滿行僅決定拼接方式，不保證能合併。

以現有聚合器執行的小型驗證：

```text
滿行「甲。」 + 「乙」        → 兩則：「甲。」、「乙」
未滿行「甲。||」 + 「乙」    → 一則：「甲。\n乙」
滿行「甲。||」 + 「乙」      → 一則：「甲。乙」
滿行「甲||」 + 短行「||」 +「乙」 → 一則：「甲\n乙」
既有短行「前一則」 + 新草稿分段     → 可能變成同一則討論
```

以上滿行資訊是測試輸入，不是線上 PTT 容量實測結果。

### 2.3 容量來源

`packages/core/src/parser.ts` 目前依 78 欄布局扣除 lead、日期、時間、帳號欄位與可選 IP 欄位，並扣除一個字串結束位置。這比固定 80 更接近原始輸入容量，但仍是「從已顯示的推文推算」，不能直接當作任一待送出推文的保證。

尤其不能把「目前文章的舊推文沒顯示 IP」當成「此帳號這次不用保留 IP」；看板設定與 guest 狀態可能不同。輸入函式的 buffer size 是否包含 NUL、提示符占位及編碼邊界，必須由官方輸入路徑與終端 transcript 一起校準，不能用嘗試塞滿再觀察截斷的方式猜。

## 3. 方案比較

### A. 完全沿用現有聚合規則

所有非末段預留 `||`，用正文、樓號前綴與 `||` 合計填到滿行判定範圍。使用者主動換行時，讓該段維持未滿行；若換行剛好位在滿行邊界，可加入僅含 `||` 的橋接事件。

優點：舊版規則可讀，不新增協定，通常具有較高的正文容量。

限制：

- `||` 也占容量；不能先切滿再追加它。
- 主動換行落在剩餘 0 或 1 欄的位置時，需要重新切段或橋接事件；空白行也會增加實體推文。
- 下一段若以 `推1樓`、`更正我在…` 等內容開頭，可能被解讀成操作；不能只按字數任意切割。
- 原文行尾本來就有 `||` 時，現有規則會吞掉它。
- `.trim()`、marker 的 `.trimEnd()` 會損失部分空白，不能承諾逐字還原。
- 五分鐘、控制事件、同作者其他連線的發言都可能打斷或污染合併。
- 沒有新草稿的開始／結束邊界；即使每一段都已正確送達，也可能接到同作者上一則，或被下一則接走。

結論：可提供「符合舊規則的分段」，但不能宣稱完整、可靠地還原任意草稿。若選此方案，需接受上述限制；不建議作為預設長期架構。

### B. 明確的版本化分段格式（推薦）

在普通 PTT 推文正文加入小型分段標頭，明確攜帶群組識別、段序、拼接方式與結束標記。底層仍盡量填滿每段，但聚合不再依靠「滿行」猜測使用者意圖。

優點：可保留主動換行、隔離不同草稿、辨認缺段、避免將正文誤判為控制命令，也可跨刷新、換客戶端重新解析。

代價：每段標頭占用容量，長文可能產生更多實體推文；舊版規則與一般 PTT 客戶端會看到標頭。這是白皮書規則的新增，不是可以偷偷放進 UI 的實作細節。

### C. 僅本機記住哪些推文屬於同一則

傳送與 A 相同，UI 用本機送出紀錄強制拼接。其他客戶端、重新登入或本機紀錄遺失後無法重建，也可能與核心聚合結果矛盾，因此不採用。

## 4. 推薦方案的 wire 草案

以下語法是待核准的候選格式，不是目前已支援的指令：

```text
~z1:<group>:<seq>:<join><end>:<payload>
```

- `z1`：分段格式版本。
- `group`：8 個小寫 base36 字元；由安全亂數產生，只用於同一文章、同一作者的群組識別，不是授權憑證。
- `seq`：從 0 開始的十進位序號，不允許前導零（0 本身除外）。
- `join`：`J` 為直接接在前段後；`N` 為先插入一個 `\n`。第 0 段必須是 `J`。
- `end`：`0` 表示後面仍有段；`1` 表示最後一段。
- `payload`：正文原樣，不遞迴解讀 `||`、推噓、回覆或編輯控制格式；允許冒號，第一個標頭結束位置之後全部屬於正文。
- `payload` 不直接包含 CR/LF；空白行可由空 payload 的 `N` 段表示，PTT 實際收到的正文仍有非空標頭。

8 字元 group、1 位 seq 的標頭為 18 個 ASCII bytes；seq 位數增加時必須重新扣除容量。此開銷需列入產品選型，不可忽略。

### 4.1 範例

以下只示意結構，不代表真實容量下的最佳切段：

```text
輸入：第一行很長…剩下的文字。\n第二行\n\n第四行

→ user: ~z1:k8m2q7va:0:J0:第一行很長…
→ user: ~z1:k8m2q7va:1:J0:剩下的文字。
→ user: ~z1:k8m2q7va:2:N0:第二行
→ user: ~z1:k8m2q7va:3:N0:
→ user: ~z1:k8m2q7va:4:N1:第四行
```

回覆其他回文時，第一段外層保留 `回12樓：`：

```text
→ user: 回12樓：~z1:k8m2q7va:0:J0:第一段
→ user: ~z1:k8m2q7va:1:J1:接續文字
```

後續段透過 group 找到第一段的對象，不依賴「最近一次發言」繼承對象，也不重複浪費樓號前綴的容量。新規則解析器必須先識別分段，再把 payload 當作純文字，不能讓它重新觸發操作規則。

### 4.2 與 `||` 的關係

- 新格式不需要自動插入 `||`；拼接由 `J/N` 決定。
- 舊推文繼續遵循 MERGE-001～003，不更改既有 `||` 語意。
- 新格式 payload 的 `||` 保留為使用者文字。
- 若採 A，才需要用 `||` 跨越終止符；它仍不能獨自解決所有換行與群組邊界問題。

### 4.3 群組判定與缺段

- 群組鍵為文章識別、正規化作者、group。段序必須唯一、遞增且原始事件順序一致。
- `seq=0` 定義新邊界，不能併入前一則舊式推文；後續無標頭推文也不能併入這個群組。
- 合法外層回覆前綴只允許在第一段；後續段若帶不同對象，視為衝突。
- 有第 0 段、所有連續序號及唯一最後段，才視為完整。不得跨過缺段直接拼接兩側文字。
- 部分資料先顯示已確認的連續前綴；孤立、重複、衝突或非法標頭保留原始事件，不吞掉文字、不執行其中的操作命令。
- group 重用或碰撞若造成重複起始／序號，整個衝突群組不得假裝完整；不能選一筆任意勝出。送出前需確認快照沒有使用相同 group。
- 明確分段群組不使用五分鐘的推測合併限制；其他人插話不改變指定群組，舊推文規則仍維持原限制。
- 第一段及後續段的原始樓號都加入同一 logical reply 的 `sourceFloors`，既有回覆任一來源樓號仍指向該討論；不得用分段序號冒充原始樓號。
- 看起來恰好符合保留語法的普通草稿，也必須封裝後送出，避免被當作標頭。歷史文章恰好符合完整語法仍有低機率誤判，須在新增白皮書規則時明列保留字串與相容性影響。

## 5. 容量、編碼與切段

### 5.1 所有檢查使用同一個傳送計畫

browser 提供與當前登入／文章工作階段綁定的容量及編碼能力；core 的純函式 planner 使用這些能力生成計畫；UI 僅消費計畫，不再自訂固定 80。

每段必須滿足：

```text
encode(外層回覆前綴 + 分段標頭 + payload).byteLength <= maxInputBytes
terminalColumns(同一完整字串) <= maxContentColumns
```

分別保存 bytes 與欄位，不把 Unicode 字元數、UTF-16 length、Big5 bytes、終端 cell 數混為一談。UAO 不支援或無法往返還原的字元在送出任何段以前拒絕，保留草稿並指出字元，不靜默替換成問號。

容量應包含帳號長度、是否保留 IP、輸入 buffer 終止位置，以及當次命令格式。缺乏可信容量時，先取得能力資料；無法取得則不送出，不用固定等待時間或猜測的 80 代替。

### 5.2 切段規則

1. 將 CRLF／CR 正規化成 LF；除此之外不自動 trim 正文。
2. 先驗證整份草稿可編碼；不能送到中途才發現後段字元不支援。
3. 先分辨使用者 LF，再在每個邏輯行內切割。每段盡量容納最多完整字元，不切斷編碼字元或可支持的字素群。
4. 自動切段使用 `J`；使用者換行使用 `N`。連續、開頭及結尾換行都由明確段落邊界表示，不依賴填充空白。
5. 標頭、seq 位數、第一段回覆前綴均納入預算。容量僅剩 1 byte 而下一字需 2 bytes 時，保留 1 byte 未使用，不塞半個字或補字。
6. 新格式的空白 payload 不再使用既有 marker stripping 的 `.trimEnd()`。PTT 若會移除行尾空白，該能力必須由 transcript 驗證；無法往返保存的字串應在 preflight 失敗，不能承諾未驗證的逐字保留。
7. 計畫包含每段 payload 範圍、完整 wire text、bytes、columns、拼接方式及目標。用真實 parser/aggregator 做往返測試，不先替 fixture 聚合。

新格式每段雖盡量填滿，但「滿行」不再是還原正確性的必要條件。

## 6. 傳送與失敗處理

```text
draft → preflight → ready → sending[i] → verifying[i] → next
                                        ├─ not-sent → paused
                                        └─ uncertain → reconciling → paused / next
全部確認 → refresh → close
```

- 新增獨立長回文 API，不讓原本 `Promise<Result<void>>` 的單則 API 悄悄變成多筆寫入。
- 同一次長回文占用一個序列化工作階段；自己的首頁載入、搜尋、refresh 或其他寫入不能插進每段之間。外部使用者與其他 PTT 連線無法被此鎖阻止。
- 每段先驗證文章身分與工作階段，再開啟輸入、送內容、確認，最後以原始事件新增證據確認。保留目前已驗證文章 session，不要求每段退出重進。
- 上一段未確認前不得送下一段；不以固定 sleep 當成功，也不平行送出。
- server 節流採明確拒絕／就緒狀態處理；不得快速盲重試。只讀確認可以重試，未知結果的寫入不能重送。
- 一般回覆文章若使用原生推／噓，只有第一段採用該類別，其餘全部為 `→`；logical reply 類別取第一段，避免每一段增加原生推噓。作者本人及回覆其他回文全部為 `→`。
- 成功收據保存完整文章識別、group、seq、wire fingerprint、新增事件位置與驗證狀態；不只比對相同文字是否曾出現。
- `not-sent`：停止後續段，保留已送進度及未送草稿。使用者可續送，重新驗證容量與文章後，只送尚未送出的段。
- `uncertain`：先讀回比對 group/seq 與新增事件。找到唯一對應才繼續；無法證明則停止，不把 refresh 成功視為該段已送出或未送出。
- 容量改變：只能重切尚未送出的部分，保留 group、已確認序號與使用者 LF 邊界。已送段不得改寫；目前不使用總段數作為 wire 契約，避免後段重新規劃使前段標頭失效。
- 使用者取消只能停止尚未送出的段，不撤銷已送段、不自動刪文或發布撤回控制命令。
- 第一版進度只存在當次連線記憶體；不將草稿、帳密或 wire text 放進一般 log。頁面重載後沒有可靠 journal 時，不自動猜測續送或重送。跨重載恢復不是本版完成條件。

## 7. 產品呈現

- 編輯器允許長文，顯示簡短的預估段數，而不是讓使用者自行符合單行長度。
- 正常送出只顯示局部進度，例如 `送出中 2/5`；完整確認並刷新後關閉窗格。
- 部分失敗不得直接關閉並丟棄未送文字。最小必要呈現為 `已送出 2/5 則` 及對應的「繼續送出」或「重新整理」操作；不顯示底層狀態機說明。
- 分段沒有跨多則的原子性。單則先前核准的「refresh 後關窗」不能套用到整批未完成的情境。
- 提案產品保護上限為每次 20 則實體推文，作為可配置的批次政策，不是 PTT 字數限制；超過時在任何寫入前保留草稿並引導改用回覆文章。此值須與方案一起核准，不將其寫死於聚合規則。

## 8. 層級責任與相容性

| 層 | 責任 |
| --- | --- |
| 白皮書／共用 fixtures | 新分段語法、J/N、群組邊界、缺段、碰撞、literal payload 與樓號定位規則；新增規則版本，不改舊 fixture expected 來迎合程式 |
| core | 純分段計畫、格式編解碼、聚合；新增長回文 command/result/progress 契約，不刪除原單則 API |
| browser | 真實編碼與容量證據、批次序列化、工作階段校驗、逐段送出與讀回；不讓 UI 操作裸終端 |
| UI | 編輯草稿、顯示預估與進度、觸發一次長回文意圖；不生成樓號／分段控制字串 |

既有實作未提供長回文能力時，新 UI 必須明確保留單則能力，不能自行用迴圈呼叫舊 API 假裝支援。新格式的 rules version、core/browser capability 與 fixture manifest 要一起更新。HTML 範例需呈現完整、缺段、插話及換行案例。

## 9. 驗證矩陣

1. 容量：帳號短／長、IP 開／關、guest、NUL 邊界、首段前綴、seq 9→10、剩 0／1 bytes、下一字為雙 byte。
2. 編碼：ASCII、中文、395 個已收錄符號混排、不支援 Emoji；拒絕時所有 write 次數為 0。
3. 文本：句號落在切點、原文 `||`、含控制命令樣式、LF 恰好落在容量邊界、連續／首尾空白行、冒號、保留語法字串、行尾空白。
4. 聚合：同作者上一則／下一則不得混入；其他人插話、同作者另一組分段、五分鐘以上、缺第 0／中段／末段、重複 seq、碰撞、倒序、非法標頭。
5. 對象／評分：回覆原始樓號而非卡片序號、聚合回文的不同來源樓號、對象撤回／變更；全部巢狀段為箭頭，一般文章推噓只計第一段。
6. 傳送：第 k 段確定拒絕、確認後斷線、讀回延遲、已有相同舊內容、容量改變、使用者取消、refresh 與寫入競爭；已確認段及 uncertain 段均不得盲重送。
7. UI：不讓使用者手動切段；送出時不能重複提交；整批成功才關窗；部分失敗保留進度與未送文字。
8. 端到端性質測試：對所有受支援草稿，planner → wire → 真實終端 parser → aggregator 的結果等於 LF 正規化後的草稿，並且每段符合實際編碼容量。不得只測 planner 的 join 結果。
9. 真實 terminal fixture：在另行授權的 Test 板實測確認輸入最大值、IP／帳號差異、行尾空白、連推節流及分段標頭完整性；本次設計工作不登入、不發送。
