# 目標 3：回文解析實作規劃

## 目的

這份文件不是任務清單，也不是改檔案清單。用途是把 [`spec.md`](spec.md) 目標 3 的規則整理成可實作的設計與限制說明，作為後續實作時的內部摘要：

- 哪些規則可以直接做
- 哪些規則需要先定義細節
- 哪些規則 technically 可做，但需要 UI 或資料模型上的限制
- 目前的 PTT 讀取方式，是否足以支撐這些規則

---

## 可實作性結論

整體來說，目標 3 是可實作的，但不是靠單一 parser 就能完成，而是需要一條完整的資料管線：

1. 先把整篇文章 raw 內容讀回來
2. 從 raw 內容中抽出 push、push 的原始位置、文章編輯紀錄與作者編輯補充文字
3. 對 raw push 做聚合
4. 建立回覆關係與巢狀樹
5. 再把結果映射成 UI 可顯示的 thread model

這代表：

- 不需要把整個看板或多頁資料先讀完
- 但需要把「單篇文章的完整 raw 內容」先讀完，才能穩定做回文解析
- 尤其是作者透過文章編輯插入的補充文字，需要依原文位置掛到最近前一則回文，必須依賴整篇文章中的原始位置資訊

---

## 核心設計原則

### 1. PTT 原始畫面仍是唯一真相來源

thread 規則不是來自 server API，而是從 PTT 文章畫面的字串中推導出來。  
因此 parser 的責任不是「猜語意」，而是：

- 保留原始順序
- 保留每一則 push 在原文中的相對位置
- 保留 `※ 編輯:` 編輯紀錄與作者編輯插入文字在原文中的相對位置
- 清掉 ANSI / backspace artifact，但不能丟失位置關係

### 2. 聚合後的回文是顯示模型，不是原始資料

原始 push 與 UI 顯示的 reply 並不是一對一。

同作者的多段推文，在符合規則時會聚合成同一則 reply。  
所以後續的：

- 樓層
- 分數
- 巢狀關係
- 作者編輯補充掛靠

都應該建立在「聚合後 reply」上，而不是原始 push 上。

### 3. 編輯紀錄與作者編輯回覆是兩種不同事件

`※ 編輯:` 本身不是作者回覆，而是文章層級的編輯紀錄。  
作者透過文章編輯實際插入的補充文字，才會在 pttzzz 的 thread model 中被視為一種 **特殊型別的 reply node**。

也就是說系統會拆出兩種事件：

- `ArticleEditRecord`：由 `※ 編輯:` 行產生，顯示在文章正文下方、回文區塊之前
- `OpEditedReplySegment`：由夾在推文區中的非一般回文文字產生，掛到最近前一則回文之下

`OpEditedReplySegment` 在樹狀結構裡和一般 reply 一樣是節點，但 UI 上會和普通 reply 做視覺區隔。

採用此設計的原因是：

- 能避免把純編輯紀錄、刪文紀錄或改錯字誤判成作者回覆
- 作者真正新增的文字才會進入 thread
- 在語意上更接近「作者對某則回覆的後續回應」
- 更符合 thread 結構本身的理解方式
- 之後如果要讓 edit 也參與更完整的 thread 行為，資料模型會比較一致

但仍然要保留兩個限制：

- `ArticleEditRecord` 不參與 thread 分數與巢狀結構
- `OpEditedReplySegment` 不參與一般推 / 噓分數統計
- 作者編輯回覆的型別仍需可辨識，不能和普通 push / boo / neutral 混成同一類

## 規則執行設計

## 1. 同作者分散回文聚合

### 規則來源

需求定義如下：

- 同作者連續回文或不連續回文，在符合續接條件時合併
- 不連續回文還需要時間間隔不大於 `k` 分鐘
- 非最終句回文若最後一字不是終止符，視為可續接
- 回文末端若有串接符號 `||`，視為明確要求與後續同作者回文合併
- 回文是否塞滿不再決定能否聚合，只決定聚合後是否直接接續上一行
- 顯示時移除 `回x樓` 前綴

### 實作方式

聚合採「單向掃描」：

1. 依文章出現順序掃過所有 raw pushes
2. 對每個作者，找最近一個可延續的聚合群組
3. 檢查是否符合合併條件
4. 若可合併，就把內容接到同一群組
5. 若不可合併，就開新群組

### 續接條件

同作者的下一則回文只有在前一段符合以下任一條件時，才會合併：

1. 前一段結尾不是終止符
2. 前一段結尾有串接符號 `||`

此規則同時套用於連續與不連續同作者回文。

不連續回文需額外滿足：

- 與前一段的時間間隔不大於 `k` 分鐘

因此「同作者臨近回文」本身不再需要塞滿單行。短的同作者回文只要沒有使用終止符，也會聚合。

`||` 是控制符，不是顯示內容。聚合輸出時會移除每一段末端的 `||`。

### 聚合後換行策略

塞滿單行只影響聚合後的顯示接法：

- 前一段若被 parser 標記為塞滿行，下一段會直接接續在同一行後方
- 前一段若未塞滿，下一段會以新的一行保留為同一個 reply block 內的獨立行

parser 會依原始 PTT 行中 content 到 IP / time 欄前的 spacing 判斷 `isFullWidthLine`。  
aggregator 優先使用此 metadata；若缺少 metadata，才 fallback 到近似 byte 長度判斷。

### 為什麼可行

因為這類規則本質上是局部決策，不需要回看整篇文章的複雜結構。  
只要 raw push 順序與時間資訊正確，就能穩定做。

### 已定義項目

`k` 分鐘固定。  
目前採用 5 分鐘，可先作為常數處理。

句尾判斷包含：

- `。`
- `.`
- `!`
- `?`
- `！`
- `？`
- `;`
- `；`

### 限制

這是 heuristic，不可能對所有非標準推文都 100% 正確。  
但 PTT 常見的「一句被切成多段推」情況是可以涵蓋的。

## 2. `回x樓` 的巢狀回覆

### 規則來源

需求定義為：

- `回x樓：...`
- `回三樓：...`
- `回 5f ...`
- `回9999F ...`
- `TO 3f ...`
- `reply to 3f ...`
- `>>1f ...`

視為該回文是對第 `x` 則原始推文樓號的回覆，並且能依此形成巢狀結構。

### 技術上是否可無窮嵌套

資料模型上可以。  
只要每一則聚合後 reply 都可以指向另一則 reply，理論上可以形成任意深度的樹。

### UI 顯示限制

如果畫面也照資料樹無限制地一直往右縮排，手機版很快就會崩。

此處區分兩層：

- **資料模型層**：支援任意深度
- **UI 呈現層**：縮排深度要有軟上限

### UI 策略

第一版採用：

- 1 到 3 層使用真實縮排
- 4 層以上不再繼續增加左縮排，只保留導線或次級背景區隔

這樣可以同時保留結構，又不會讓內容寬度被吃光。

### `x` 的編號定義

這一點已定案：

- `回x樓` 的 `x` 指向 **原始 PTT 推文樓號**
- 判定方式是 **一行一樓**
- 這個樓號不因聚合而改變
- `x` 可以是阿拉伯數字，也可以是中文數字

也就是說，`回3樓` 的語意不是：

- 第一層聚合回文中的第 3 樓
- 也不是目前 UI 顯示順序中的第 3 則聚合回文

而是：

- 原始 PTT 推文序列中的第 3 樓

### 定義原因

此定義用於持續與原始 PTT 用法兼容。

如果 `回x樓` 改去指聚合後的樓層，會產生兩個問題：

1. 同作者多段回文被合併後，原本使用者理解的樓號會改變
2. UI 呈現方式一旦改變，`回x樓` 的解讀也會跟著漂移

所以 `rawFloor` 必須是一個穩定、不受 UI 與聚合策略影響的基準。

### 對資料模型的影響

這代表系統裡至少要保留兩套識別資訊：

1. `rawFloor`
   - 原始 push 的樓號
   - 一行一樓
   - 用來解釋 `回x樓`

2. `aggregatedReplyId`
   - 聚合後 reply 的 id
   - 用來做 UI 顯示、score、作者編輯補充掛靠

因此一則聚合後回文不能只保留自己的文字內容，還必須保留：

- 它是由哪些原始樓號組成的

可概念化為：

```ts
interface AggregatedPush {
  id: string;
  sourceFloors: number[];
}
```

### `回x樓` 的實作方式

實作時應該這樣做：

1. 先對每一則 raw push 編 `rawFloor`
2. 做同作者聚合時，把原始樓號一起收進 `sourceFloors`
3. 遇到樓層引用 prefix 時，先把樓層 token 解析成數字
4. 再查是哪一則聚合後回文的 `sourceFloors` 包含這個 `x`
5. 最後把目前這則聚合回文掛到那個聚合回文之下

第一版支援的樓層引用 prefix：

- `回x樓`
- `回xf` / `回xF`
- `TO xf`
- `reply to xf`
- `>>xf`

其中 `x` 支援：

- 阿拉伯數字，例如 `3`、`9999`
- 常見中文數字，例如 `三`、`十三`、`二十一`、`一百二十三`

若 `x` 指向不存在的原始樓號：

- 該回文維持第一層
- 不移除原始 prefix
- 不掛到任何父回文底下

這樣才能保證：

- `回x樓` 的解讀永遠與原始 PTT 使用習慣一致
- 聚合不會破壞樓號語意
- 巢狀回覆仍能在聚合後資料模型中成立

### 與巢狀深度的關係

這個設計也代表：

- 巢狀回覆的目標定位是靠 `rawFloor`
- UI 深度只是顯示結果，不參與 `回x樓` 的語意判定

所以即使之後 UI 改成：

- 只顯示一層
- 折疊深層回覆
- 第 4 層後不再增加縮排

都不會影響 `回x樓` 的語意。

## 3. 文章推噓分數

### 規則來源

需求定義為文章總分只看聚合後第一層回文的推 / 噓數。

### 實作方式

- 先完成聚合
- 再只統計 `replyTo === null` 的聚合回文
- `push = +1`
- `boo = -1`
- `neutral = 0`

### 是否可行

完全可行，而且相對單純。  
這條規則不依賴 UI，也不依賴文章編輯紀錄。

---

## 4. 單則回文的推噓分數

### 規則來源

需求定義為將某則回文底下收到的推 / 噓綁到該聚合回文本身。

### 實作方式

這條依賴前一步先建好 `replyTo` 關係。

做法是：

1. 每則聚合回文先有自己的 `id`
2. 其他回文若 `replyTo = 該 id`
3. 就把它的 push / boo 加總到父回文的 `score`

### 是否可行

可行，但要注意這個 `score` 是「子回覆反應」，不是文章原生 push count。  
因此 UI 上不應偽裝成 PTT 原生推噓數，應顯示為 thread score 或回覆分數。

---

## 5. OP 標示

### 規則來源

作者自己的回文需標成原發文者。

### 實作方式

把聚合後 reply 的作者與文章作者比對即可。  
這條規則不困難。

### 需注意

文章作者欄位若帶暱稱，例如：

- `poggssi (冠軍車手321)`

而 push 作者只有帳號：

- `poggssi`

那就不能直接全文字比對。  
應該先抽出作者帳號部分再比。

---

## 6. 作者編輯與作者補充回覆

### 規則來源

規則定義如下：

- `※ 編輯:` 本身是文章編輯紀錄
- 作者透過文章編輯插入的文字，才視為對最近回文的回覆
- 回文被刪除或純編輯紀錄不需推導，保留為 PTT 原始編輯紀錄即可

### 可行性

此規則可行，但必須避免把 `※ 編輯:` 本身當成回文。

第一版採用可觀察的版面 heuristic：

- 在推文區中，兩個一般回文 marker 之間若出現非一般回文格式的文字，視為作者透過編輯插入的補充文字
- 若同區間也出現 `※ 編輯:`，該行只作為文章編輯紀錄，不作為回覆內容
- 該區間內所有非一般回文、非 `※ 編輯:`、非空白雜訊的文字，視為同一段作者補充回覆
- 這段作者補充回覆會聚合成一個特殊型別的 reply node
- `※ 編輯:` 行本身只生成文章層級的編輯紀錄，不插入回文區塊

前提是：

- 每一則聚合回文都要有可比較的來源位置
- 每段作者補充回覆，也要有可比較的來源位置

這就是為什麼 parser / adapter 不能只傳乾淨文字，還要保留 raw offset。

### 實作方式

1. 在 parser 階段抽出每個 `※ 編輯:` 行成為 `ArticleEditRecord`：
   - `marker`
   - `content`
   - `rawBlock`
   - `markerOffset`
2. 在 parser 階段掃描推文區間，抽出 `OpEditedReplySegment`：
   - 區間起點是某則一般回文
   - 區間終點是下一則一般回文，或文章結尾
   - 區間內非一般回文、非 `※ 編輯:` 的文字合併成同一段補充回覆
   - `contentAnchorOffset` 使用補充文字的起始位置
3. 在 adapter 階段為每一則 push 建立 `anchorOffset`
4. 在 adapter 階段把 `OpEditedReplySegment` 的 raw 區段從 push parsing input 中遮掉，避免它被當成上一則推文的 continuation
5. 在 aggregator 階段，對每個 `OpEditedReplySegment` 找：
   - `anchorOrder < segment.contentAnchorOffset`
   - 且最接近 `segment.contentAnchorOffset` 的那一則聚合回文
6. 找到目標後，產生 `type = "edit"` 的特殊 reply node，作者固定為原作者
7. `ArticleEditRecord` 原樣保留給 UI 顯示，不參與 thread 掛靠

### 不採用 `※ 編輯:` 標記行作為 reply 的原因

PTT 文章可能有多次編輯，但每次編輯不一定代表新增回文；也可能只是刪除文字、修錯字或更新標點。  
若把 `※ 編輯:` 本身插入回文區，會導致純編輯紀錄被誤顯示成作者回覆。

因此第一版採用：

- `※ 編輯:` = 文章層級編輯紀錄
- 推文區中夾在一般回文之間的非一般回文文字 = 作者補充回覆

此做法仍是 heuristic，不嘗試還原真正 diff，但能避免最常見的空白編輯紀錄誤判。

### 是否需要整篇文章先讀完

需要。

因為這條規則本質上是位置比較。  
若只取得部分文章，或只取得目前視窗內的幾行，無法穩定判斷「最近前一則回文」。

但只需要「整篇文章」即可，不需要整個看板歷史。

### 作者編輯回覆要不要算成一般回覆

這裡定案為：

- 作者編輯插入的補充文字在 thread model 中算是一種 reply node
- 但它是 `edit` 類型，不是普通 push / boo / neutral

因此比較合理的資料模型會是：

```ts
type ThreadNodeType = "push" | "boo" | "neutral" | "edit";
```

UI 上採用：

- 仍然顯示成獨立格子
- 但用不同背景、邊框或標頭，讓使用者知道它是作者編輯補充，不是普通推文

這樣可以兼顧：

- thread 結構一致
- 與「視為回覆」的規則一致
- 視覺上又不會和普通 reply 混淆

## 7. IP 顯示規則

### 規則來源

IP 不混入正文，只在 hover 作者時顯示。

### 實作方式

這條應該在 parser 層完成：

- 把 IP 從 raw push content 中拆出
- 存成 metadata
- 正文只保留真正內容

UI 層只負責：

- hover 作者時顯示 IP tooltip
- 不在主文字中重複顯示

### 可行性

此規則可行。  
因為 IP 是 metadata，不應該算內容本體。

## 實作需要的資料條件

## 1. 不需要整個看板資料

目標 3 的規則全部只依賴「單篇文章」。

所以不需要：

- 把整個看板先抓完
- 把多頁文章列表抓完
- 把整串討論歷史從其他頁面拼起來

## 2. 需要整篇文章 raw 內容

至少要包含：

- 正文
- push 區
- `※ 編輯:` 編輯紀錄
- 推文區中夾在一般回文之間的作者補充文字
- 文章尾部資訊

因為：

- push 聚合需要完整 push 區
- 作者補充回覆掛靠需要完整文章中的相對位置
- 壓縮同列 push / ANSI artifact 也要在 raw text 中處理

## 3. 不採用單頁內容解析

如果只根據「目前 terminal 顯示頁」解析：

- 會漏掉跨頁推文
- 會漏掉後段 `※ 編輯:` 編輯紀錄與作者補充文字
- 會讓聚合結果依賴目前畫面位置，變得不穩

所以 parser 必須吃「整篇文章」而不是單頁。

## UI 顯示策略

## 1. 第一版顯示策略

第一版採用：

- 第一層回文卡片式顯示
- 巢狀回覆顯示在父卡片底下
- 作者編輯補充顯示為特殊 reply node
- 文章編輯紀錄顯示在文章正文最下方、回文區塊之前的小區塊

這樣可維持作者補充文字為特殊 reply node，同時不把純編輯紀錄混入回文區塊。

## 2. 巢狀過深時的顯示限制

第一版採用：

- 資料模型不限制深度
- 視覺縮排限制在 3 層
- 更深的層級只保留導線與背景區隔，不再繼續右移

## 3. 預設展開策略

第一版採用：

- 全展開所有回覆
- 不做折疊

優先順序是先把語意做對。  
規則穩定後可再增加：

- 預設只展開第一層
- 第二層以上可折疊
- 深層 thread lazy render

這些都屬於後續 UX 優化，不影響規則正確性。

## 實作順序

這裡不列檔案，只列邏輯順序。

### 階段 1：先把 raw parsing 做穩

先處理：

- IP 抽取
- multiline push
- `※ 編輯:` 編輯紀錄抽取
- 作者編輯補充文字抽取
- raw offset 保真
- ANSI / backspace artifact 對位置的影響

這一層不穩，後面全部都會漂。

### 階段 2：建立聚合後的 thread model

再處理：

- 同作者多段聚合
- `回x樓` 關係
- OP 標示
- article score
- reply score
- 作者編輯補充回覆掛靠

這一層完成後，資料語意才算完整。

### 階段 3：把 model 接進 article 讀取流程

此階段重點：

- adapter 給出的 thread data 已經是完整的
- UI 不需要再自己猜 parser 規則
- hook 只負責傳遞，不負責做語意判斷

### 階段 4：最後再做 UI

待資料穩定後再處理：

- 作者編輯補充回覆呈現
- 文章編輯紀錄區塊
- 深層回覆顯示策略
- hover IP

這樣 UI 不會反覆返工。

## 已定案項目

目前已定案的產品規則如下：

1. 句尾終止符包含 `。`、`.`、`!`、`?`、`！`、`？`、`;`、`；`
2. `k` 固定為 5 分鐘
3. 資料模型支援深層巢狀，但 UI 最多只做 3 層視覺縮排
4. 第一版採用全部展開，不做折疊
5. `※ 編輯:` 視為文章層級編輯紀錄，顯示在文章正文下方、回文區塊之前
6. 作者透過文章編輯插入的補充文字，視為特殊型別的 reply node，掛到最近前一則回覆之下，且 UI 會與普通 reply 做視覺區隔
7. 同作者回文只有在前一段可續接時才聚合；塞滿單行不是聚合必要條件
8. `||` 可作為回文末端串接符號，強制與後續同作者回文合併，且不進入顯示內容
9. 塞滿單行只影響聚合後的換行策略：滿行直接接續，未滿行保留為同一 reply block 內的新行

## 結論

此需求在技術上可實作，但需接受以下限制：

- thread 規則必須建立在整篇文章 raw 內容上
- 巢狀回覆資料上可無窮深，但 UI 不應無限制縮排
- `回x樓` 的編號語意已定義為原始 PTT 推文樓號，一行一樓
- `※ 編輯:` 已定案為文章層級編輯紀錄，不是 reply node
- 作者編輯插入的補充文字才是特殊型別的 reply node
- 聚合規則本質上有 heuristic 成分，目標是讓大多數 PTT 實例正確，而不是追求 100% 無歧義

目前版本可視為目標 3 的已決策設計摘要。
