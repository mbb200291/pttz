# Goal 8 Follow-up：投票狀態與文章投票隱藏設計

## 背景

Goal 8 第一階段已阻止同一個尚未完成的回文投票請求被快速連點重複送出，並將回文分數統一為明確投票的淨值。實站驗證仍發現以下問題：

- 點擊已選取的回文推或噓會在本地變成未投票，但沒有送出撤回指令；再次點擊可重送相同方向。
- Optimistic state 目前不會在重新載入後清除，因而持續覆蓋解析結果。
- PTT ID 比對目前區分大小寫，使同一帳號的不同字形無法互相移除。
- 文章推噓按鈕送出的單獨 `推`、`噓` 仍顯示成討論串卡片。
- 實站截圖顯示扣分按鈕送出的 `噓` 使用了 `→` 類別；目前流程固定等待後若未辨識推文類型選單，便會直接送出內容。

## 目標

- 同一帳號對同一回文只保留最後一個有效方向。
- 在尚未實作撤回前，點擊已選方向不得改變狀態或再次送出。
- 文章投票事件保留於統計資料，但不出現在討論串。
- 系統送出的推／噓必須使用相符的 PTT 推文類型；無法確認時回報失敗。

## 文章投票事件

聚合回文的內容經 `trim()` 後若恰好為以下值，即視為文章投票事件：

```text
推
噓
```

規則如下：

- `推` 的語意方向為 push，`噓` 的語意方向為 boo。
- 語意方向以內容為準，可修正既有資料中內容為 `噓`、PTT marker 卻為 `→` 的顯示與統計。
- 事件保留在 article data 中，供文章推、噓數與文章分數計算。
- 完整討論串、第一層回文總數、回文排序及 progressive loading 都排除這類事件。
- `推 好文`、`噓 原因` 等含其他文字的內容不是文章投票事件，仍顯示為一般回文。
- `推x樓`、`噓x樓` 仍沿用回文投票規則，不與本規則混用。

共用的純函式負責辨識文章投票方向，避免完整畫面、partial 畫面及統計各自實作不同判斷。

## 回文投票狀態機

回文投票只有 push 與 boo 兩個已選狀態；在 Goal 9 撤回功能完成前，不允許由 UI 產生本地 `0` 狀態。

| 目前狀態 | 點擊推 | 點擊噓 |
|---|---|---|
| 未投票 | 送出 `推x樓` | 送出 `噓x樓` |
| 已推 | 不動作 | 送出 `噓x樓` |
| 已噓 | 送出 `推x樓` | 不動作 |

送出成功後，optimistic state 立即只保留新方向並觸發重新載入。當新的 article data 中該使用者的解析方向與 optimistic 方向一致時，移除該回文的 override，回歸 parser 結果。送出或 reload 失敗時解除 pending 鎖並保留最後 optimistic 狀態；同方向重點擊仍由狀態機阻擋。

## ID 正規化與最後一票

PTT ID 比對採 ASCII 不分大小寫：

```text
MBB200291 == mbb200291
```

聚合器以正規化 ID 作為同一目標回文的 voter key。掃描原始推文時只保存每個 ID 的最後方向，再由最終 map 建立互斥的 `pushVoters` 與 `booVoters`，避免以陣列逐步增刪時留下同一帳號的兩種大小寫。

UI 判斷目前使用者投票與 optimistic 更新時使用同一個正規化規則。切換方向會從舊方向扣一並在新方向加一，不從可能過期的原始 voter 陣列重建兩份名單。

## PTT 推文類型送出

`submitPushFromCurrentArticle` 不再只固定等待 180ms 後讀取一次畫面。流程改為：

1. 送出 `X`。
2. 等待推文類型選單或可判定的內容輸入／失敗畫面。
3. 選單出現時選擇 push 對應的 `1`、boo 對應的 `2`、一般回文對應的 `3`。
4. 確認已進入內容輸入階段後才送出內容。
5. 如果要求 push 或 boo 卻無法確認類型選單，不送內容、取消流程並回傳失敗；neutral 保留看板直接進入內容輸入階段的相容路徑。

這項修正同時適用文章投票與回文投票，因兩者共用 adapter 寫入入口。

## 元件與資料流

### `pushAggregator.ts`

- 提供文章投票事件辨識 helper。
- 使用正規化 voter key 建立互斥的最後方向名單。
- `calcArticleScore` 對單獨 `推／噓` 使用內容語意方向，其餘第一層推文沿用 PTT marker。

### `Article.tsx`

- partial 回文清單排除文章投票事件。
- 文章統計以文章投票 helper 修正單獨 `推／噓` 的方向。
- 回文投票不再建立假的撤回狀態。
- optimistic count 從目前顯示狀態切換方向。
- 新 article data 確認相同方向後清除該回文的 optimistic override。

### `PushThread.tsx`

- 建立 top-level 與 children map 前排除文章投票事件。
- 已選方向再次點擊只傳回同方向，由 Article handler 判定為無操作，不產生 `0`。

### `adapter.ts`

- 等待並確認推文類型選單。
- 推或噓類型無法確認時安全取消，不送出內容。

## 錯誤處理

- 同方向重複點擊是無操作，不顯示錯誤。
- 不把 push／boo 自動降級為 neutral。
- 類型選單逾時沿用 action failure 管道回報，並解除對應 pending 狀態。
- 不對 PTT 寫入做自動重試，避免不確定狀態下重複發文。
- 本地 optimistic state 不得讓同一使用者同時貢獻推與噓。

## 測試與驗收

### 文章投票隱藏

- 單獨 `推` 與 `噓` 不出現在完整討論串。
- 單獨 `推` 與 `噓` 不出現在 partial 回文清單。
- 隱藏事件不計入第一層回文數與排序。
- `推 好文`、`噓 原因` 仍顯示。
- marker 為 `→`、內容為 `噓` 的既有資料仍視為文章噓。

### 回文最後一票

- 已推再點推不呼叫 `votePush`，畫面維持已推。
- 已噓再點噓不呼叫 `votePush`，畫面維持已噓。
- 推改噓後只顯示噓，噓改推後只顯示推。
- `MBB200291` 與 `mbb200291` 視為同一 voter。
- 原始序列 `推1樓、推1樓、噓1樓、推1樓` 最終只有一個 push voter，沒有 boo voter，score 為 `+1`。
- 新 article data 確認相同方向後，不再由舊 optimistic state 覆蓋 parser 結果。

### PTT 類型

- 類型選單延遲出現時仍先選擇正確類型，再送內容。
- push 送 `1`、boo 送 `2`、neutral 送 `3`。
- push／boo 類型選單逾時時不送內容並回傳失敗。

### 完整驗證

```bash
npm test
npm run lint
npm run build
```

不使用真實帳號進行寫入測試；實站驗證需由使用者另行授權並提供測試條件。

## 不採用方案

- 不從 aggregator 刪除單獨 `推／噓`：刪除會使文章統計失去資料。
- 不只在卡片 render 時隱藏：partial 畫面、回文總數及排序仍會短暫或間接包含它。
- 不新增通用 event hierarchy：目前只需要一個共用辨識 helper，額外抽象沒有收益。
- 不將同方向重點擊視為撤回：Goal 9 尚未具備可持久化的 PTT 撤回指令。
