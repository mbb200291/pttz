# pttz 白皮書
> 規則版本：0.4.0-dev

本白皮書提出一套在不更動既有 PTT 資料格式的前提下，將終端文章與推文解析成現代論壇討論結構的方法。文件聚焦於跨實作共用的語意、規則與風險，不規定特定介面的視覺呈現。

提案分為三個概念層級：

```text
規則層
定義推文如何合併、嵌套、評價、編輯與撤回
        ↓
核心實作層
讀取 PTT 資料，套用規則，輸出穩定的文章、討論結構與操作
        ↓
介面層
依核心輸出實作網頁、行動裝置或其他形式的使用者介面
```

白皮書本身屬於規則層；核心實作與介面實作可以有多種形式，只要遵守相同規則與資料契約，就可得到一致的語意結果。完整畫面對照見[核心規則案例集](./core-rules-examples.html)，可執行的規則案例見[討論事件 fixtures](../fixtures/thread-events/README.md)。

規則版本採語意化版本：不改變規則語意的澄清或案例修正升修訂版；相容的新規則升次版；重解釋既有規則或改變既有輸出語意升主版。`-dev`為開發中版號

## 解析規則提案

透過在推文中增加解析規則，以讓進階的功能得以實現。但PTT原生介面仍然可支援，因此以下規則的設計盡可能保有自然語言語意，並且維持簡潔、最少干擾，避免過度影響原生 PTT 閱讀體驗。

### A 原始推文、樓號與事件

#### RAW-001 名詞定義

1. **推文**：文章下方以 PTT 原生 `推`、`噓`、`→` 類別發出的單元，統稱為「推文」。
2. **正向推文／負向推文／中立推文**：依 PTT 原生類別，分別指 `推`、`噓`、`→`。
3. **文章**：透過發文功能建立的獨立內容單位；其中的文字內容稱為「文章內文」。
4. **推總數／噓總數**：依本提案規則，對文章或推文計算的正向、負向評價數量。
5. **回文**：透過文章回覆功能建立、用以回應既有文章的另一篇文章。
6. **語法格式**：本提案定義、具有特定解析用途的文字格式，例如嵌套目標、評價、編輯、撤回及續接標記。
7. **一般推文／指令推文**：不帶有可辨識語法格式的推文稱為「一般推文」；帶有可辨識語法格式的推文稱為「指令推文」。指令推文不一定隱藏，其語法是否生效及如何呈現，依各項規則判定。
8. **純指令推文**：該推文沒有可見正文，系統將不顯示其文字。
9. **合併推文**：多則推文滿足合併規則後形成的單一單位，保留各來源推文及其原始樓號。
10. **嵌套推文**：以另一則推文為回應目標，而非直接回應文章的推文。
11. **正文**：推文中供閱讀的文字內容；指令推文的正文不包含依規則移除的語法格式。
12. **事件**：從推文中依語法格式與解析規則辨識出的行為紀錄，例如新增推文、評價、編輯或撤回。一則推文可以產生一個或多個事件；事件保留來源推文、操作者與作用目標，是否生效依各項規則判定。
13. **原始推文／原始樓號**：PTT 中尚未套用本提案規則的一筆推文，稱為「原始推文」；依其在文章中的原始順序分配的編號，稱為「原始樓號」。
14. **前綴**：原始推文的文字從第一個字元開始，符合本提案語法格式的起始部分。辨識時不忽略開頭空白；前綴後的分隔符與正文要求，依各項規則判定。
15. **尾標**：忽略原始推文的文字末端的半形空白（U+0020）與全形空白（U+3000）後，最後一個字元若為 `|` 或 `\`，即稱為尾標；否則視為沒有尾標。
16. **評價**：對文章或推文表達正向「推」或負向「噓」的行為。依目標區分為「文章評價」與「推文評價」

#### RAW-002 原始推文與樓號

1. 每一筆原始推文都依 PTT 順序占一個樓號，包括後續可能被隱藏的指令推文。
2. 同一筆原始推文產生多個事件時，這些事件共用來源樓號，不另占樓號。
3. 所有 `x樓`／`xF` 都以原始樓號定位。
4. 合併推文保存全部來源樓號，因此指向其中任一樓，都視為指向同一則合併推文。
5. 合併、嵌套或隱藏推文不會重新編排原始樓號。
6. 介面中卡片的順序與數量不代表 PTT 原始樓號。
7. 先依原始推文的文字辨識最外層語法及其有效性，再處理可見推文的尾標與合併。
8. 指令推文移除已辨識語法格式後的正文，不再遞迴辨識其他語法格式。

### B 合併回文

#### MERGE-001 合併規則

1. 同作者依原始樓號順序最接近的前後兩筆推文，不滿足以下任一「排除條件」，且滿足以下任一「合併條件」者，將兩則推文合併為一則。

   排除條件
   - 任一筆是不形成可見正文的控制推文。
   - 後者推文符合嵌套語法格式，且指定的目標與前者所屬合併推文的目標不同。
   - 任一筆推文時間不可解析，或後者時間早於前者。
   - 前者推文的尾標為 `\`。

   合併條件
   - 兩筆推文的原始樓號直接相鄰。
   - 兩筆推文的發文時間間隔不超過兩分鐘（`0 ≤ B time - A time ≤ 2 min`）。
   - 前者推文的尾標為 `|`（見 MERGE-003 強制續接）。

2. 顯示時間以後一則推文的時間為代表。
3. 合併規則會依原始樓號順序遞迴向下套用到全部推文。
4. 兩筆之間若夾有其他作者的控制推文，不影響合併，其事件仍依原始樓號順序處理。
5. 指向任一來源樓號的評價，作用於該樓所屬的合併推文。

#### MERGE-002 滿行與未滿行合併

1. 若依原始 PTT 終端欄位配置計算後，推文正文剩餘可輸入欄寬不足一個全形中文字，視為已占滿正文可用區域，兩段內容直接連接。
2. 若推文未占滿正文可用區域，則視為作者故意換行，合併後在兩個片段之間插入換行。
3. 終端畫面造成的物理折行，應在解析單一原始推文時先還原，不參與不同原始樓號之間的拼接判斷。
4. 無法保留或可靠判斷原始欄位間距時，採保守策略插入換行。

#### MERGE-003 強制續接

1. 原始片段的尾標為 `|` 時，稱為「續接符」，不受兩分鐘合併規則限制，可拼接推文。
2. 無後續片段時，已辨識的續接符尾標仍不顯示。

#### MERGE-004 強制分段

1. 原始片段的尾標為 `\` 時，稱為「分段符」，阻止後方片段接入該群組。

#### THREAD-006 發送長推文

1. 系統補入的嵌套前綴與尾標均占每段 PTT 傳送容量。
2. 超過 PTT 單則容量的推文將拆為多筆推文依序發送。
3. 單則推文容量包含嵌套前綴與尾標，以實際編碼計算，不截斷內容與拆開單個字元。
4. UI 實作層可自訂單次發送分段上限。
5. 系統送出的推文，最後一則須加尾標 `\`，未切分的推文亦同，避免後方推文與其合併。
6. 補入嵌套前綴或尾標後超過容量時，須重新切分。
7. 自動切出的滿行依 MERGE-002 直接串接。
8. 主動換行落在滿行位置時，可插入正文僅有續接符（`|`）的橋接推文，以保留換行；嵌套前綴依原目標處理。
9. 切分前，先去除整份草稿末尾連續的半形空白、全形空白與換行符號。
10. 草稿中除了末尾外的空白行須保留。
11. 使用中立推文（PTT 原生 `→`）發出。

### C 嵌套推文

#### THREAD-001 嵌套目標格式

1. 行首為以下格式之一時，視為指定回覆對象，且x樓號早於自己樓號：
   - `回x樓`
   - `回xf`／`回xF`
   - `TO xf`／`TO xF`
   - `reply to xf`／`reply to xF`
   - `>>xf`／`>>xF`
2. 上述格式後必須至少間隔有一個半形或全形空白、`:` 或 `：`。
3. 呈現時移除上述回覆格式，剩餘內容掛到 xF 所屬的合併回文。
4. 移除格式後的內容不再遞迴解析其他控制格式。
5. 若該樓不存在或是為隱藏之控制事件時，保留原文為一般回文。

#### THREAD-002 推噓加文字同時構成回覆

1. 以下文字格式起始的回文，若在間隔有一個半形或全形空白、`:` 或 `：`之後有其他文字，則將其後續的文字視為對回文的嵌套回覆，並採計一個推至該目標回文。
   - `推x樓`
   - `x樓推一個`
2. 以下文字格式起始的回文，則將其後續的文字視為對回文的嵌套回覆，並採計一個噓至該目標回文。
   - `噓x樓`
3. 以下文字格式起始的回文，則將其後續的文字視為對前一樓的嵌套回覆，並採計一個推至該目標回文。
   - `推樓上`
4. 以下文字格式起始的回文，則將其後續的文字視為對前一樓的嵌套回覆，並採計一個噓至該目標回文。
   - `噓樓上`
5. 呈現時移除上述回覆格式，剩餘內容掛到 xF 所屬的合併回文。
6. 若上述格式後方文字沒有間隔一個半形或全形空白、`:` 或 `：`，則不視為控制事件，也不採計推噓分。
7. 若後方沒有其他文字，則視為純推噓事件，不建立可見回文，僅單純採計推噓計分。（相關規則見#### VOTE-002 回文推噓）

#### THREAD-003 不跨回覆對象

1. 沒有新回覆格式的續行，可繼承上一片段的回覆對象。
2. 若新的片段明確指定不同回覆對象，則不得與上一群組合併。

#### THREAD-004 嵌套顯示深度

1. 核心資料始終保留原始回覆對象。
2. 介面層可調整顯示層級，但不得改變核心保存的原始回覆對象、樓號、定位或推噓對象；最大顯示深度與超深回覆的呈現方式由各介面實作自行定義。

#### THREAD-005 回覆樓上

1. 行首的 `回樓上` 格式，且在間隔有一個半形或全形空白、`:` 或 `：`之後有其他文字，視為對樓上的回文。
2. 若上述格式後沒有一個半形或全形空白、`:` 或 `：`，則視為一般回文。
3. 呈現時移除上述回覆格式，剩餘內容掛到 xF 所屬的合併回文。
4. 樓上固定指緊鄰上一筆原始 PTT 推文樓號。
5. 該來源樓號若已聚合，則指向整張聚合卡。
6. 純回文投票隱藏並沿用 VOTE-002，PTT 原生分數仍另外保留。
7. 前一樓不存在或是隱藏控制事件時，保留原文為一般回文。
8. 實作pttz之系統，發送回覆與投票時，使用明確原始樓號，不使用回覆樓上此類格式。

#### VOTE-001 文章推噓

1. 文章推噓以 PTT 原始推文類別計算：`推` 計入文章的推，`噓` 計入文章的噓，`→` 不計入
2. 依 THREAD-001、THREAD-002 或 THREAD-005 歸入某則回文的可見嵌套回覆，其 PTT 原始推噓類別不計入文章推噓，避免對回文的回覆同時改變文章評價。
3. 依 VOTE-002 識別出的純回文推噓若由其他客戶端以 PTT `推` 或 `噓` 類別送出，視為嵌套回文，不計入文章推噓總數
4. 實作本提案的客戶端依 VOTE-002 使用 `→`，因此不會額外影響文章推噓。
5. 回文內容除去前後空白後僅有 `推` 或 `噓` 時，視為純文章推噓控制事件，不在系統顯示
6. 方向仍以 PTT 原始推文類別為準，且事件本身不顯示為回文。未排除任何語意事件的 PTT 原生推噓分數可另外保留顯示，供使用者對照原始 PTT 結果。

#### VOTE-002 回文推噓

1. 以下格式位於回文內容行首時，視為對 xF 所屬回文的推：
   - `推x樓`
   - `x樓推一個`
2. 以下格式位於回文內容行首時，視為對前一樓回文的推：
   - `推樓上`
3. 以下格式位於回文內容行首時，視為對 xF 所屬回文的噓：
   - `噓x樓`
4. 以下格式位於回文內容行首時，視為對前一樓回文的噓：
   - `噓樓上`
5. 若以上符合格式後方沒有接續任何文字，則視為純回文推噓，不顯示此回文，僅有保留推噓數在目標回文上。
6. 若以上格式後方，間隔至少一個空格（全形或半形、`:`、`：`)，後方文字視為對該回文的回文（嵌套回文）
7.  有剩餘內容時，依 THREAD-002 同時形成嵌套回覆。
8.  回文推噓方向由內容格式決定，不由 PTT 原始推文類別決定。
9.  透過本提案實作的系統發送回文推噓時，應使用 PTT `→` 類別，避免額外影響文章推噓與 PTT 原生推噓分數。
10. 控制事件的正負方向仍計入原始 PTT 推、噓

#### VOTE-003 同帳號推噓去重

1. 同一帳號對同一目標回文最多計入一票。
2. 同方向重複推噓不重複計票。
3. 若之後改為相反方向，則以最新有效方向為準。
4. 本提案實作的發送端應阻止同方向重複發送；解析端仍須容納其他客戶端產生的重複事件。

#### VOTE-004 推文評價撤回

1. 使用以下格式撤回既有推文評價：
   - `撤回我對x樓的推`
   - `撤回我對x樓的噓`

2. 只有當目前有效推噓方向與撤回方向一致時，才清除該帳號對 xF 的推噓狀態。
3. 系統產生此類事件時使用 PTT `→` 類別。
4. 此類控制事件不顯示為一般回文。

#### VOTE-005 文章推噓撤回

1. 撤回文章的推時，以 PTT `噓` 類別送出純內容 `噓`。
2. 撤回文章的噓時，以 PTT `推` 類別送出純內容 `推`。
3. 由於原始 PTT 資料無法區分「撤回」與「反向投票」，同作者對文章的第二筆反向純推噓視為抵銷，並清除 pttz 的應用層投票狀態。
4. 抵銷後再次出現同方向或反方向事件時，再依事件順序建立新的應用層狀態。
5. 每筆抵銷事件的原始推文類別仍照常計入提案的文章推噓與未經語意排除的 PTT 原生推噓分數。

### E 編輯與撤回回文

#### EDIT-001 回文補充與修改

1. 帳號只能修改相同帳號過去發出的回文。
2. 編輯事件以原始樓號定位被修改的回文。
3. 若該樓屬於一則由多個原始樓號合併而成的回文，核心仍須保留各原始片段與其修改關係。

#### EDIT-002 回文區段修改

1. 系統產生的局部修改可使用以下格式，同時表達插入、刪除與替換：
   - `^start:end=替代內容`
   - 以一個字符為單位（UTF-16 code unit），從 `0` 起算，修改範圍包含 `start`、不包含 `end`，也就是 `[start, end)`。
   - `start = end` 時在該位置插入文字；替代內容為空時刪除該範圍；其餘情況以新文字替換該範圍。

2. 多個修改區段以 `;` 分隔，並由右至左套用：
   - `^2:2=新增;^8:10=新的文字`

3. `start` 與 `end` 皆以編輯前的回文內容為基準；每個範圍都必須位於 `0` 至正文長度之間，且不得互相重疊。
4. 區段修改只作用於回文文字，不重新解析其中的回覆、推噓或其他控制語法。
5. 區段修改格式應包覆於一般編輯指令中，例如：
   - `更正我在30樓發言：^2:3=讚讚`

#### EDIT-003 回文撤回

1. 以下格式視為撤回既有回文：
   - `撤回我在x樓的發言`
   - `撤回我在x~y樓的發言`

2. 帳號只能撤回相同帳號過去發出的回文。
3. 撤回後該回文不再顯示正常內容；介面保留作者、時間及撤回占位，不顯示原文、歷史內容或操作按鈕。
4. 占位不計入有效回覆數。
5. 原始樓號及既有父子關係仍保留，不因撤回重新編號；子回覆仍位於撤回占位下，不提升層級，也不因父回覆撤回而遺失編輯結果。
6. 核心可使用單一空格作為撤回內容的占位值。

#### EDIT-004 編輯內容不重新解析

1. 編輯事件只解析最外層的編輯指令。
2. 補充、替換或區段修改產生的新文字內容視為不透明內容。
3. 編輯後內容即使包含 `回x樓`、`推x樓`、撤回指令或其他控制格式，也不得重新解析為新的語意事件。
4. 編輯不得改變原事件既有的回覆對象、推噓對象或其他結構性語意。

### F 原發文者

#### OP-001 原發文者標示

1. 當回文作者與文章原發文者為同一帳號時，該回文應標示為原發文者。
2. 帳號比對不區分英文字母大小寫。
3. 原發文者標示僅表示作者身分，不影響回文的合併、嵌套、推噓或樓號。

#### OP-002 原發文者於推文區域的文章編輯

1. 原發文者透過文章編輯，在推文區域中插入的文字，視為原發文者的一則回覆。
2. 該回覆以前方位置最接近的回文為回覆對象。
3. 該回覆標示為原發文者，並顯示為目標回文的嵌套回覆。
4. 此類回覆由文章本文產生，不占用 PTT 原始推文樓號。
5. 若其前方不存在可作為回覆對象的回文，則不將該文字解析為嵌套回覆。
6. 此類回覆的內文不做另外控制符號的解讀，所有內文都是嵌套回文內容。

#### OP-003 文章內文的編輯

1. 核心應解析文章編輯紀錄，使介面能將修改歷程與文章內文分開呈現。

## 規則邊界和系統風險

1. 作者從 PTT 原生系統編輯文章時，可能移動或刪除系統用來辨識嵌套關係的文字，進而破壞既有解析結果。
2. PTT 沒有原生推文編輯功能。補充、更正與撤回依賴語法格式，仍會在原生閱讀體驗中引入額外文字。
