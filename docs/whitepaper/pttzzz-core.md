# PTTzzz 提案白皮書

## 讓 PTT 重生

> 讓我們一同打造新生的 PTT。
>
> 我們提案重新解析終端頁面，讓 PTT 在保有原始文化與資料的同時，往現代化社群論壇推進。合併分散推文、建立嵌套回文、加入回文推噓與回文編輯 —— 這只是開始。
>
> 我們不只想讓 PTT 繼續存在，更要推動它重生，成為下一個世代依然充滿生命力的社群。
>
> 這場改造，沒有終點。

這份白皮書旨在提出一套讓現有 PTT 架構能支援現代化論壇結構的改進方向。不更動既有 PTT 資料，而是透過具語意的解析規則，在既有資料之上實現現代論壇所需的功能。

此提案除了白皮書外，另提供一份對白皮書規則的核心實作，以及相容此核心實作的網頁介面實作。在AI的時代，我相信在基於此白皮書的明確規範下，我們能輕易的實現核心層和介面層的實作，讓每個人都能有自己想要的ptt閱讀體驗。

此份提案會陳述核心概念、解析規則、實作方向與可能風險，並附上一份核心實作與介面實作作為參考。

參考核心實作 `@pttzzz-core` 放置於 `/packages`；介面實作 `@ptt-client-browser`、`@pttzzz` 則放置於 `apps/`。

技術附錄保留實作需要的精確邊界，更多畫面對照見[核心規則完整案例集](./core-rules-examples.html)。

## 核心提案

### 一、將分散推文合併

PTT 的一段話經常受單行長度限制而被拆散，閱讀者必須自行判斷哪些推文原本屬於同一段發言。我們提案將這些分散片段重新合併，使完整觀點能以一則連貫回文呈現。

### 二、讓對回文的回覆顯示為嵌套結構

PTT 的推文依時間排列，卻難以直接看出一句話正在回應誰。我們提案辨識推文中的回覆意圖，把線性事件還原成具有上下文的嵌套討論，讓讀者能沿著對話關係理解爭論、補充與延伸，而不必在樓號之間來回尋找。

### 三、區分文章推噓與回文推噓

PTT 原生推噓只能直接表達對整篇文章的態度，無法清楚評價討論中的某一則觀點。我們提案區分文章推噓與回文推噓：保留文章整體評價，也讓參與者能對具體回文表示贊同或反對。

文章推噓沿用 PTT 原始的推、噓類別；一般頂層回文也會影響文章推噓，但已歸入某則回文之下的嵌套回覆不採計，避免同一句回覆同時改變文章與回文的評價。

單純用於推噓的事件可以在呈現上隱藏，避免推噓訊息干擾討論閱讀。

### 四、回文的編輯與撤回

PTT 的回文送出後便無法直接修改。我們提案讓使用者能補充、更正或撤回自己的發言，同時保留原始樓號與討論脈絡。

## 套用案例

### 案例一：交錯推文仍可合併

| PTT 原始畫面 | 提案的呈現結果 |
| --- | --- |
| <pre>12F alice: 我覺得這個功能<br>13F bob: 我倒是沒什麼感覺<br>14F alice: 對閱讀體驗幫助很大</pre> | <pre>alice  12F, 14F<br>┌──────────────────────┐<br>│ 我覺得這個功能       │<br>│ 對閱讀體驗幫助很大   │<br>└──────────────────────┘<br><br>bob  13F<br>┌──────────────────────┐<br>│ 我倒是沒什麼感覺     │<br>└──────────────────────┘</pre> |

#### 說明

alice 的兩筆推文雖然被 bob 的留言插入，但作者與回覆對象相同，且時間差仍在允許範圍內，因此可重新合併成同一則回文。

### 案例二：三層嵌套，各層都可合併

| PTT 原始畫面 | 提案的呈現結果 |
| --- | --- |
| <pre>10F alice: 第一層上半句<br>11F alice: 第一層下半句<br>12F bob: 回10樓 第二層上半句<br>13F bob: 第二層下半句<br>14F carol: >>12F 第三層上半句<br>15F carol: 第三層下半句</pre> | <pre>alice 10F~11F<br>├─ 第一層上半句<br>│  第一層下半句<br>│<br>└─ bob 12F~13F<br>   ├─ 第二層上半句<br>   │  第二層下半句<br>   │<br>   └─ carol 14F~15F<br>      第三層上半句<br>      第三層下半句</pre> |

#### 說明

合併先保留來源樓號，嵌套關係再以原始樓號定位各層回文。

### 案例三：文章推與回文推不同

| PTT 原始畫面 | 提案的呈現結果 |
| --- | --- |
| <pre>12F → alice: 我覺得這個功能很好用<br>20F 推 dora: 推<br>21F → dora: 推12樓</pre> | <pre>文章<br>推 +1<br><br>alice  12F    推 +1<br>┌────────────────────────┐<br>│ 我覺得這個功能很好用   │<br>└────────────────────────┘</pre> |

#### 說明

dora 的純 `推` 使用 PTT 原生推類別，因此計入文章推噓；`推12樓` 使用 `→` 類別，只作用於 12F 所屬回文。兩者都是純推噓事件，因此本身不顯示為回文。

### 案例四：一筆事件同時推噓與回覆

| PTT 原始畫面 | 提案的呈現結果 |
| --- | --- |
| <pre>12F → alice: 我支持這個方案<br>22F 推 erin: 推12樓 我同意</pre> | <pre>文章                       推 0<br><br>alice 12F                 推 +1<br>└─ erin 22F<br>   我同意</pre> |

#### 說明

`推12樓` 決定對 12F 的推噓；其後的「我同意」使同一事件成為可見的嵌套回文。即使原始事件使用 PTT 推類別，既然整筆事件已歸入 12F 的嵌套討論，就不再計入文章推噓。

### 案例五：回文修改與撤回

| PTT 原始畫面 | 提案的呈現結果 |
| --- | --- |
| <pre>30F frank: 我覺得原本的方案比較好<br>31F grace: 這個功能沒有必要<br>32F frank: 更正我在30樓發言：我覺得新的方案比較好<br>33F grace: 撤回我在31樓發言</pre> | <pre>原始呈現<br><br>frank  30F<br>┌──────────────────────────┐<br>│ 我覺得原本的方案比較好   │<br>└──────────────────────────┘<br><br>grace  31F<br>┌──────────────────────────┐<br>│ 這個功能沒有必要         │<br>└──────────────────────────┘<br><br>套用修改與撤回後<br><br>frank  30F<br>┌──────────────────────────┐<br>│ 我覺得新的方案比較好     │<br>└──────────────────────────┘<br><br>grace  31F<br>┌──────────────────────────┐<br>│                          │<br>└──────────────────────────┘<br>（已撤回）</pre> |

#### 說明

32F 修改 frank 在 30F 的內容；33F 撤回 grace 在 31F 的發言。修改與撤回事件本身不形成新的可見回文，30F 與 31F 的原始樓號仍保持不變。

### A 樓號、原始事件與控制事件

#### RAW-001 原始事件與樓號

1. 每一行原始推文事件都依 PTT 順序占一個樓號，包括後續可能被隱藏的純推噓、編輯與撤回事件。
2. 所有 `x樓`／`xF` 都以原始樓號定位。
3. 合併回文保存全部來源樓號，因此指向其中任一樓，都視為指向同一則合併回文。
4. 合併、嵌套或隱藏事件不得重新編排原始樓號。
5. 介面中卡片的順序與數量不代表 PTT 原始樓號。
6. 控制事件為用於改變既有資料狀態，而本身不形成一般可見回文的事件，例如純推噓、推噓撤回、回文編輯與回文撤回。

### B 合併回文

#### MERGE-001 合併規則

1. 合併要求作者與回覆對象相同。
2. 連續片段不受時間差限制。
3. 不連續片段須能解析時間，且相差不超過五分鐘。
4. 作者不同、回覆對象不同、控制事件、時間不可解析或超時，均切斷合併。
5. 前一片段若以 `.。!?！？;；` 結束，預設切斷合併。

#### MERGE-002 滿行與未滿行拼接

1. 若依原始 PTT 終端欄位配置計算後，回文正文剩餘可輸入欄寬不足一個全形中文字（少於兩個終端欄位），視為已占滿正文可用區域；下一則回文視為可能因長度限制而續寫，兩段內容直接串接。
2. 若回文已未占滿正文可用區域，則視為作者主動另起一筆，在兩個片段之間插入換行。
3. 終端畫面造成的物理折行，應在解析單一原始事件時先還原，不參與不同原始樓號之間的拼接判斷。
4. 無法保留或可靠判斷原始欄位間距時，採保守策略插入換行。
5. 滿行判斷只決定文字如何拼接，不影響能否合併。

#### MERGE-003 強制續接

1. 前一回文片段末尾為 `||` 時，可越過終止符強制允許後續片段續接。
2. `||` 不顯示於最終內容。
3. `||` 不放寬作者相同、回覆對象相同，以及不連續片段五分鐘內等其他合併條件。

### C 回文回覆

#### THREAD-001 嵌套目標格式

1. 行首為以下格式之一時，視為指定回覆對象：
   - `回x樓`
   - `回xf`／`回xF`
   - `TO xf`／`TO xF`
   - `reply to xf`／`reply to xF`
   - `>>xf`／`>>xF`
2. 上述格式後必須為字串結尾、半形或全形空白、`:` 或 `：`。
3. 呈現時移除上述回覆格式，剩餘內容掛到 xF 所屬的合併回文。
4. 移除格式後的內容不再遞迴解析其他控制格式。

#### THREAD-002 推噓加文字同時構成回覆

1. `推x樓`、`x樓推一個`、`噓x樓` 後若仍有文字內容，同一事件同時：
   - 更新目標回文的推噓。
   - 將剩餘內容建立為對該回文的嵌套回覆。
2. 純推噓事件沒有剩餘內容時，不建立可見回文。

#### THREAD-003 不跨回覆對象

1. 沒有新回覆格式的續行，可繼承上一片段的回覆對象。
2. 若新的片段明確指定不同回覆對象，則不得與上一群組合併。

#### THREAD-004 嵌套顯示深度

1. 核心資料始終保留原始回覆對象。
2. 介面層可調整顯示層級，但不得改變核心保存的原始回覆對象、樓號、定位或推噓對象；最大顯示深度與超深回覆的呈現方式由各介面實作自行定義。

### D 對文章和回文的推噓

#### VOTE-001 文章推噓

1. 提案的文章推噓以 PTT 原始推文類別計算：`推` 計入文章的推，`噓` 計入文章的噓，`→` 不計入。一般頂層回文也依此計算，內容不必是純 `推` 或純 `噓`。
2. 依 THREAD-001 或 THREAD-002 歸入某則回文的可見嵌套回覆，其 PTT 原始推噓類別不計入文章推噓，避免對回文的回覆同時改變文章評價。
3. 依 VOTE-002 識別出的純回文推噓若由其他客戶端以 PTT `推` 或 `噓` 類別送出，視為嵌套回文，不計入文章推噓總數；本提案的發送端依 VOTE-002 使用 `→`，因此不會額外影響文章推噓。
4. 回文內容除去前後空白後僅有 `推` 或 `噓` 時，視為純文章推噓控制事件；方向仍以 PTT 原始推文類別為準，且事件本身不顯示為回文。未排除任何語意事件的 PTT 原生推噓分數可另外保留顯示，供使用者對照原始 PTT 結果。

#### VOTE-002 回文推噓

1. 以下格式位於回文內容行首時，視為對 xF 所屬回文的推：
   - `推x樓`
   - `x樓推一個`

2. 以下格式位於回文內容行首時，視為對 xF 所屬回文的噓：
   - `噓x樓`
3. 上述格式後必須為字串結尾、空白、`:` 或 `：`，避免一般文字被誤判。
4. 沒有剩餘內容的純回文推噓不顯示為回文。
5. 有剩餘內容時，依 THREAD-002 同時形成嵌套回覆。
6. 回文推噓方向由內容格式決定，不由 PTT 原始推文類別決定。
7. 透過本提案實作的系統發送回文推噓時，應使用 PTT `→` 類別，避免額外影響文章推噓與 PTT 原生推噓分數。

#### VOTE-003 同帳號推噓去重

1. 同一帳號對同一目標回文最多計入一票。
2. 同方向重複推噓不重複計票。
3. 若之後改為相反方向，則以最新有效方向為準。
4. 本提案實作的發送端應阻止同方向重複發送；解析端仍須容納其他客戶端產生的重複事件。

#### VOTE-004 回文推噓撤回

1. 使用以下格式撤回既有回文推噓：
   - `撤回我對x樓的推`
   - `撤回我對x樓的噓`

2. 只有當目前有效推噓方向與撤回方向一致時，才清除該帳號對 xF 的推噓狀態。
3. 系統產生此類事件時使用 PTT `→` 類別。
4. 此類控制事件不顯示為一般回文。

#### VOTE-005 文章推噓撤回

1. 撤回文章的推時，以 PTT `噓` 類別送出純內容 `噓`。
2. 撤回文章的噓時，以 PTT `推` 類別送出純內容 `推`。
3. 由於原始 PTT 資料無法區分「撤回」與「反向投票」，同作者對文章的第二筆反向純推噓視為抵銷，並清除 PTTzzz 的應用層投票狀態。
4. 抵銷後再次出現同方向或反方向事件時，再依事件順序建立新的應用層狀態。
5. 每筆抵銷事件的原始推文類別仍照常計入提案的文章推噓與未經語意排除的 PTT 原生推噓分數。

### E 編輯與撤回回文

#### EDIT-001 回文補充與修改

1. 帳號只能修改相同帳號過去發出的回文。
2. 以下格式視為補充內容，將內容附加至該樓或該樓所屬合併回文：
   - `補充我在x樓說的：<內容>`
   - `補充我在x樓發言：<內容>`
   - `續xF：<內容>`

3. 以下格式視為替換內容：
   - `修正我在x樓的說法：<內容>`
   - `更正一下我在x樓的回覆：<內容>`
   - `更正我在x樓發言：<內容>`
   - `更正我在xF的留言：<內容>`

4. 編輯事件以原始樓號定位被修改的回文。
5. 若該樓屬於一則由多個原始樓號合併而成的回文，核心仍須保留各原始片段與其修改關係。

#### EDIT-002 回文區段修改

1. 系統產生的局部修改可使用以下格式，同時表達插入、刪除與替換：
   - `^start:end=替代內容`
   - 位置從 `0` 起算，修改範圍包含 `start`、不包含 `end`，也就是 `[start, end)`。
   - `start = end` 時在該位置插入文字；替代內容為空時刪除該範圍；其餘情況以新文字替換該範圍。

2. 多個修改區段以 `;` 分隔，並由右至左套用：
   - `^2:2=新增;^8:10=新的文字`

3. `start` 與 `end` 皆以編輯前的回文內容為基準；每個範圍都必須位於 `0` 至正文長度之間，且不得互相重疊。
4. 區段修改只作用於回文文字，不重新解析其中的回覆、推噓或其他控制語法。
5. 區段修改格式應包覆於一般編輯指令中，例如：
   - `更正我在30樓發言：^2:3=讚讚`

#### EDIT-003 回文撤回

1. 以下格式視為撤回既有回文：
   - `撤回我在x樓的發言`
   - `撤回我在x~y樓的發言`

2. 帳號只能撤回相同帳號過去發出的回文。
3. 撤回後該回文不再顯示正常內容。
4. 原始樓號仍保留，不因撤回重新編號。
5. 核心可使用單一空格作為撤回內容的占位值。

#### EDIT-004 編輯內容不重新解析

1. 編輯事件只解析最外層的編輯指令。
2. 補充、替換或區段修改產生的新文字內容視為不透明內容。
3. 編輯後內容即使包含 `回x樓`、`推x樓`、撤回指令或其他控制格式，也不得重新解析為新的語意事件。
4. 編輯不得改變原事件既有的回覆對象、推噓對象或其他結構性語意。

### F 原發文者

#### OP-001 原發文者標示

1. 當回文作者與文章原發文者為同一帳號時，該回文應標示為原發文者。
2. 帳號比對不區分英文字母大小寫。
3. 原發文者標示僅表示作者身分，不影響回文的合併、嵌套、推噓或樓號。

#### OP-002 原發文者於推文區域的文章編輯

1. 原發文者透過文章編輯，在推文區域中插入的文字，視為原發文者的一則回覆。
2. 該回覆以前方位置最接近的回文為回覆對象。
3. 該回覆標示為原發文者，並顯示為目標回文的嵌套回覆。
4. 此類回覆由文章本文產生，不占用 PTT 原始推文樓號。
5. 若其前方不存在可作為回覆對象的回文，則不將該文字解析為嵌套回覆。

#### OP003 文章本文的編輯

1. 對文章編輯紀錄解析，並適當呈現編輯紀錄

## 實作架構提案

我們提案將實作分成三層：白皮書作為規則層，定義期望的語意與結果；核心層將原始 PTT 資料套用白皮書規則，輸出穩定的資料與操作；介面層則依據核心層輸出實作網頁、行動裝置或其他形式的使用者介面。

```text
規則層
定義推文如何合併、嵌套、推噓、編輯與撤回
        ↓
核心層
讀取 PTT 資料，套用規則，輸出穩定的文章與討論結構
        ↓
介面層
以網頁、行動介面或其他形式呈現，並透過核心執行操作
```

## 規則邊界和系統風險

1. 作者從ptt原生系統對文章的編輯，可能會嚴重破壞對回文的解析
2. 對回文編輯，為了最小化干擾，需引入編輯語法這類相對非語意的規則
